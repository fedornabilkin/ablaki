# Парольный вход в админку перед отключением записей старого сайта

Проверка 2026-11-17, только локальные изолированные fixtures. Production-БД и учётные данные владельца не использовались. Изменения не опубликованы.

## Найденное расхождение

API `/login` и админка `/user/security/login` используют наследников общей `common/models/user/PasswordLoginForm`, вызывающей `PasswordVerifier`. Она поддерживает современный bcrypt и старый `md5(sanitized_password . md5(salt))`, включая историческую обработку спецсимволов. При входе пароль и salt не переписываются; современный hash не допускает отката к старому паролю.

Однако API явно отключал обязательное подтверждение email, а backend наследовал противоположные defaults Dektrium. Поэтому старый пользователь с `confirmed_at = NULL` мог пройти API-пароль, но получить отказ в админке. Этот случай воспроизведён изолированным тестом с реальными merged-конфигурациями. Привязка к конкретному production-аккаунту без серверной диагностики не подтверждена.

В `backend/config/main.php` явно выставлена та же confirmation policy, что у API. Проверка blocked_at и административные права остаются. Аутентификация сама по себе не выдаёт p-admin; существующие RBAC/CSRF-фильтры не изменены. API использует bearer token, админка — собственную session/cookie: одинаковой должна быть проверка пароля и допуска аккаунта, а не способ хранения сессии.

## Проверки

Из `yii2/`: `php tests/release/auth-response.php`. Используется только in-memory SQLite; ничего не загружается из production .env. Проверены:

- Старый и современный пароль, логин/email, спецсимволы, сохранение hash/salt и отказ на неверный пароль.
- Одинаковая эффективная confirmation policy API/admin и вход без confirmed_at/auth_key; парольный вход в админку не требует выдачи токена старым сайтом.
- Сохранение блокировки аккаунта; явная строгая confirmation policy по-прежнему проверяется отдельными случаями.
- Сохранение существующего API token lifecycle и старого admin key-login с ротацией и невозможностью повторного использования потреблённого ключа.

SQLite проверяет этот auth-контракт, но не заменяет транзакционные/конкурентные проверки целевых СУБД для миграции данных.

## Production-приёмка до SELECT-only музея

1. Выпустить проверенное исправление отдельно от переключения БД. Сверить точный deployed SHA, backend module modelMap/confirmation policy и возможные main-local.php overrides. Не печатать пароли, hash, salt или auth_key.
2. В приватном окне открыть обычную форму админки `/user/security/login`, войти логином/паролем существующего администратора **без посещения генератора токена старого сайта**. Проверить сессию и доступ к разрешённому разделу по p-admin. Выход/повторный вход проверить отдельно.
3. Проверить парольный вход нового frontend; различать неверные credentials, блокировку аккаунта, отсутствие p-admin, CSRF/cookie/session и ошибку БД. При отказе исследовать сообщение/логи с удалёнными секретами, не сбрасывать password/auth_key для обхода.
4. Только после успешной приёмки закрыть задачу C6 и переводить старый сайт на SELECT-only. Старую генерацию токенов не считать обязательной зависимостью новой системы. Изменение/удаление существующего key-login — отдельная задача, в этом исправлении он сохранён.
