Дата: 2026-10-31. Исходный код аудита: `feature/09-worlds` / `3a7deef`. После подготовки движков прошли **59/59 миграций**, seed и повтор `world-setup/install`; схема версии **44**, флаги доступа и экономики остались выключены. Это подтверждает установку. Актуальное решение по деньгам, backup и условному разрешению production приведено ниже; прежние выводы аудита сохранены как история проверки.

Уточнение владельца: старые таблицы создавались вручную до появления миграций. Для установки мира используем только его отдельную команду; адаптация всей старой vendor-схемы не является предварительным условием этой задачи.

## Решение владельца и проверка горячего обновления

**Последующее уточнение:** владелец разрешил оставить сайт доступным и временно отклонять денежные операции на время переноса (локально около 9 минут). Поэтому перенос конкурентных денежных изменений без паузы больше не нужен. Перед DDL необходимо установить совместимую защиту писателей, завершить старые запросы и сохранить чтение сайта. Доступ к GitHub Actions восстановлен через штатную авторизацию Windows; подготовлен отдельный read-only production preflight без деплоя.

Уточнение 31 октября после полного дампа: 119 дробных личных остатков разрешено перенести в точный формат; отрицательные остатки рекламы признаны устаревшими, их не менять и не считать блокером. Новый дамп с остановкой записи владелец отменил. Production через GitHub Actions разрешён условно: после успешной проверки на временной БД. Повторное разрешение на сам выпуск не требуется; технические ошибки должны быть устранены до его запуска.

Проверка на той же MariaDB 10.1.48 выявила реальный блокер горячего перехода: `ALTER ... MODIFY credit DECIMAL(19,4), ALGORITHM=INPLACE, LOCK=NONE` возвращает **1846**, `Cannot change column type INPLACE`. Предлагаемый сервером `ALGORITHM=COPY` не является переносом без блокировки записи. Существующий `WalletRollout` также является offline-процедурой: он замораживает денежные операции, сохраняет полный снимок, затем сверяет его перед активацией. Удалять эту защиту или выдавать её за горячую миграцию нельзя.

Отдельно обнаружена разница между нативным FLOAT→DECIMAL и согласованным десятичным округлением исходного текстового значения. Она затрагивает 12 личных остатков (до 0,0008 Cr), 443 473 значения истории остатка и 155 исторических изменений (до 0,0031 Cr). Это отдельный эффект двоичного FLOAT, а не дополнительные пользователи, которым требуется произвольная корректировка. Перенос должен сохранять рассчитанное значение из снимка, а не результат обычного ALTER.

Подготовлена явная политика `half-up-4`, сохраняемая в журнале переноса новой миграцией `m261031_210000_wallet_precision_policy`. По умолчанию остаётся `strict`; обычный денежный парсер не округляет. Оригиналы и точные значения остаются в `economy_wallet_snapshot`, история сохраняет отрицательные списания. После DDL явный перенос приводит значения к проверенному снимку и сверяет его контрольные суммы. Это процедура переноса при остановленных денежных операциях. Работу чтения и завершение старых запросов обеспечивает отдельная совместимая защита и сценарий ниже. Для изолированной репетиции политика выбирается позиционным аргументом `world-setup/wallet-freeze half-up-4`.

Проверка второго соединения: начисление после снимка вызывает отказ до ALTER; новое начисление не перезаписывается. Смена политики на середине переноса и преждевременная активация отклоняются. Устаревшие отрицательные рекламные значения отражаются отдельным счётчиком `historical_negative_ignored`; положительные некорректные суммы и нетранзакционные таблицы по-прежнему блокируют активацию.

Исходный дамп остаётся материалом репетиции; он не объявляется согласованной точкой восстановления. Отказ от нового backup принят и сам по себе больше не является блокером. Первоначальные ограничения авторизации устранены. Read-only Actions подтвердили MariaDB 10.1.48, отсутствие триггеров, наличие совместимой защиты и выключенную денежную паузу. Перед основным выпуском обязательны полный CI и проверки новой процедуры подготовки; параллельные денежные записи на время переноса запрещены согласованной паузой.

## Сценарий production при доступном сайте

Владелец явно разрешил временный отказ денежных операций. Подготовительная версия уже установлена; создание `yii2/common/runtime/financial-maintenance/paused` включает HTTP 503 с `Retry-After` для операций изменения. Известные маршруты чтения остаются доступными. Старые изменяющие GET-маршруты не исключаются из защиты только из-за метода GET.

`deploy/world-production-upgrade.sh` проверяет каталог `/var/www/api.ablakin.ru`, ветку `master`, точный проверенный SHA, чистоту checkout и неизменность runtime/Composer/Compose. Контейнеры приложения и база не пересоздаются. До первой DDL-команды сценарий:

1. Сохраняет маркер паузы, останавливает запуск новых cron-задач.
2. Плавно перезагружает PHP-FPM и ждёт завершения старых процессов и CLI-команд; nginx продолжает работать.
3. Получает исключительную файловую блокировку, общую с запросами приложения. Проверяет доступность API чтения.
4. Обновляет код до проверенного SHA. Отдельный CLI-процесс проверяет production-контекст, версию/имя БД, маркер паузы и внешнюю блокировку.
5. Переводит 12 финансовых таблиц в InnoDB. Перед и после каждой DDL сверяет число/хеш строк, столбцы и индексы; сохраняет контрольную точку перед неоткатываемым DDL.
6. Выполняет только `world-setup/install` (60 миграций и seed), затем сохранённые фазы `half-up-4`: snapshot → convert → verify → activate. Число округлённых личных остатков вычисляется по свежему production-снимку, а не по старому списку пользователей из дампа.
7. Проверяет выключенные флаги игрового мира, доступность чтения и запуск cron. Только затем удаляет паузу и освобождает блокировку.

При ошибке маркер остаётся на месте; повтор того же проверенного выпуска продолжает сохранённые фазы. Нельзя вручную удалять `paused`, переводить DECIMAL обратно во FLOAT или откатывать приложение на версию без защиты. После начала DDL применяется исправление вперёд с сохранением снимков; данный сценарий не обещает восстановление несогласованного исходного dump. Файлы контрольных точек и диагностический журнал остаются вне Git на сервере.

Этот этап подготавливает схему и точный кошелёк. Он не включает игровой мир, NPC-фонд, storage/accounts rollout и не начисляет тестовые средства. Эти этапы имеют отдельные критерии активации.

Повторная свежая Windows-копия подтвердила новую проверку всех 12 InnoDB-конверсий, но вновь получила файловый отказ 1025/13 при изменении `world_node`. Успешная полная репетиция первой копии сохраняется; повреждённая копия не выдаётся за успешное восстановление. Дополнительно введён Linux CI на MariaDB 10.1.48 с production-кодировкой и ограничениями Antelope/large_prefix=OFF. На Linux изолированная проверка переноса/повтора DDL уже прошла; полный прогон выполняется после приведения кодировки тестовой БД к production.

## Установка только мира: необходимая подготовка

1. Использовать восстановленную полную копию MariaDB 10.1.48 для репетиции; новый backup с остановкой записи отменён владельцем. Перед production устранить ограничения горячего перехода из раздела выше и проверить выбранную последовательность на Linux с production-настройками.
2. Проверить актуальные FK/индексы и данные крафта: обязательную строку `craft_meta.id=1`, ссылки владельцев/предметов, дубли и количества. Снять `php yii world-audit/schema`, `php yii world-audit/data`, `php yii world-audit/credits` из проверенного checkout. Сохранить отчёты и исходные остатки.
3. Для самого `world-setup/install` по текущему CSV нужно перевести две обязательные таблицы из MyISAM в InnoDB. Остальные таблицы предварительной проверки уже InnoDB. Следующие команды проверены на копии; их нельзя выдавать за готовую последовательность горячего production-обновления:

   ```sql
   ALTER TABLE history_balance ENGINE=InnoDB;
   ALTER TABLE history_rating ENGINE=InnoDB;
   ```

   Проверить число строк, содержимое, суммы и индексы до/после. Для последующего включения денежных операций нужен более широкий список InnoDB из `world-audit/credits`, включая игровые таблицы, комиссию, переводы и форумные подарки; двух таблиц для активации недостаточно.
4. Из каталога `yii2`, с проверенным подключением к нужной базе, выполнить только:

   ```bash
   WORLD_INSTALL=confirmed-world-install php yii world-setup/install
   ```

   Команда проверяет предпосылки, запускает `@console/world-migrations` и начальное заполнение. Старые vendor/обычные миграции она не запускает. Некоторые world-миграции также изменяют существующий крафт и наполняют справочники — это не только создание новых пустых таблиц. После ошибки остановиться, устранить причину и повторить штатную команду, сохраняя уже записанную историю; не запускать все файлы вручную заново.
5. Проверить все 59 записей world-миграций, схему и сохранность старых данных. Установка не включает мир автоматически. Перенос wallet/storage/accounts, проверка резервов и включение доступа выполняются отдельными этапами. Не использовать `test-ready` или тестовое пополнение на production.

В окно установки не запускать общий `migrate/up` без ограничения каталога и не использовать перезапуск старого entrypoint как замену отдельной команде мира: entrypoint запускает также прежние миграции. Историю вручную созданных таблиц не переписывать ради установки мира.

## Обнаруженные несовместимости

### 1. Повторное создание существующей таблицы подарков

`forum_comment_gift` есть (по снимку 0 строк), но `m260905_120000_create_forum_comment_gift_table` в истории отсутствует. MySQL DDL показывает уникальный индекс и два вспомогательных индекса, но не внешние ключи. С учётом ручного создания старых таблиц это не доказательство частичного сбоя. Фактическая проблема возникает при попытке повторно запустить создание таблицы общей цепочкой миграций; отдельная установка мира эту миграцию не выполняет.

Текущий исходный код сразу выполнял `CREATE TABLE` и падал с «table already exists». После устранения этого препятствия FK на `forum_comment` всё равно не создастся: родитель — MyISAM. Это проверено на отдельной MariaDB.

Исправлено локально: повтор использует существующую таблицу, проверяет определения именованных индексов и достраивает отсутствующие индексы/FK, сохраняя записи. Проверка InnoDB выполняется до DDL; движок автоматически не меняется. MySQL DDL выполняется без внешней `safeUp`-транзакции. Перед production-повтором нужны InnoDB и проверка дублей/сирот, а не ручная отметка миграции как выполненной.

### 2. История денег и рейтинга — MyISAM, установка мира останавливается

`persone` и `user` уже InnoDB; переводить их «на всякий случай» не требуется. `history_balance` и `history_rating` — MyISAM: их запись нельзя откатить вместе с изменением счёта. MyISAM также используется играми, переводами, обменом и комиссиями.

Воспроизведён сбой `m261017_120000_world_economy_profiles`: FK `credit_transfer_history.history_id → history_balance.id` не создаётся. Проверка `wallet-freeze`/активации также требует транзакционные таблицы.

Добавлена предварительная проверка `world-setup/install` до запуска миграций и создания их журнала: наличие базовых таблиц и InnoDB у таблиц, необходимых для хранения активов и установки мира. Результат доступен в `world-audit/schema` как `installation_prerequisites`; в обычный отчёт включён `history_rating`. Проверка не заменяет аудит всех старых финансовых операций.

Список MyISAM из снимка:

`advertising`, `bonus`, `comission`, `credit_exchange`, `credit_transfer`, `fact`, `forum_awards`, `forum_comment`, `forum_theme`, `game_duel`, `game_five`, `game_five_hod`, `game_orel`, `game_saper`, `history_balance`, `history_rating`, `konkurs`, `mailer`, `notice_mail`, `payments`, `seif`, `set`, `settings`, `slider`, `temp`, `todo`, `wiki_categories`, `wiki_copy`, `wiki_pages`.

Для финансовой совместимости как минимум нужно рассмотреть перевод `advertising`, `comission`, `credit_exchange`, `credit_transfer`, всех пяти `game_*`, обеих `history_*`, `forum_comment` в InnoDB. Остальные таблицы — отдельный перечень по потребителям; массовый `ALTER` на всех таблицах без проверки не подготовлен и не выполнялся. Конвертация движка перестраивает таблицу и может блокировать её; сначала измерить на копии, проверить объём свободного диска, индексы и сравнить содержимое до/после.

### 3. Старые вручную созданные таблицы авторизации

В истории отсутствуют все **12** `m[0-9]*` миграций установленного `dektrium/yii2-user`. Entry point первым запускает именно этот каталог. Первая миграция пытается создать уже существующий `user`; следующие предполагают старые поля и таблицу `account`, а часть удаляет/переименовывает поля. Исполнять их целиком или просто пометить всю цепочку выполненной нельзя.

Схема отличается от конечной vendor-схемы: `user.id` unsigned; `username` nullable `varchar(25)`; у `profile.user_id` нет PK и допускается NULL; `profile.bio` — `varchar(255)`. Таблицы `token` и `social_account` в CSV отсутствуют. Поля пароля/соли необходимо сохранить побайтно. По одной структуре нельзя решить, есть ли повторные профили/логины и какие сценарии восстановления/подтверждения аккаунта реально используются.

По уточнению владельца эти таблицы исторически создавались вручную. Отсутствие записей не требует изменения авторизации перед установкой мира. Старую vendor-цепочку исключаем из маршрута установки мира; если позже потребуется запускать именно её или расширять функции авторизации, сначала отдельно сопоставим необходимую схему и данные. Vendor-файлы, пароль, соль и история миграций не изменялись. Повторный `CREATE user/profile` остаётся ошибочным действием, но не является препятствием для отдельного `world-setup/install`.

### 4. Остальные обычные миграции и перенос суммы подарка

В `console/migrations` отсутствуют четыре записи:

1. `m260905_120000_create_forum_comment_gift_table` — описана выше.
2. `m260911_120000_convert_forum_text_to_utf8`.
3. `m260911_130000_normalize_forum_utf8`.
4. `m260919_120000_add_forum_gift_amount`.

Две UTF-8 миграции преобразуют `forum_theme`/`forum_comment`; обе сохраняются в порядке истории. Таблицы имеют utf8, поэтому нужен контроль кириллицы, длинных сообщений и уникальности после преобразования. Не нужно выполнять глобальную перекодировку всех cp1251/latin1 таблиц.

Миграция `amount` раньше безусловно добавляла столбец и смешивала DDL с переносом данных в `safeUp`. Теперь столбец добавляется только при отсутствии, а транзакция переноса начинается после DDL. При некорректной сумме истории вся партия изменений откатывается; повтор возможен без удаления столбца. Дробные суммы больше не обрезаются до целого молча. Существующее поведение восстановления сумм 1–3 сохранено.

Каталоги binds, redirect и RBAC новых файлов относительно предоставленной истории не имеют. В журнале не отражены 16 файлов из обычных путей (12 vendor + 4 приложения), но это не список обязательных работ: часть схемы создана вручную. Для отдельной установки мира нужны его 59 миграций. Старые изменения рассматриваются по фактической схеме и используемым функциям.

### 5. MariaDB 10.1.48 и данные — отдельные условия выпуска

Фактически MariaDB **10.1.48**, Ubuntu 18.04. `innodb_large_prefix=OFF`, `innodb_file_format=Antelope`, default row format `COMPACT`, page size 16384; `innodb_strict_mode=OFF`. Индексируемые строки нужно проверять по байтам: COMPACT ограничивает префикс 767 байт; произвольное расширение уникального `utf8mb4 varchar` до 255 здесь небезопасно. [Документация MariaDB](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-row-formats/innodb-compact-row-format).

Рекомендуется отдельный переход на поддерживаемую LTS MariaDB, с закреплением конкретного maintenance-пакета и проверкой на нём до выпуска. 10.1 не входит в поддерживаемые Community LTS; актуальные сроки опубликованы в [политике MariaDB](https://mariadb.org/about/#maintenance-policy). Локальная 10.11.8 использовалась на первом этапе для воспроизведения ошибок, а не выбрана как окончательная версия production. Новый прогон на 10.1.48 описан ниже. Прямое обновление серверных пакетов 10.1 без репетиции не предлагается: предпочтителен отдельный новый сервер и логический перенос прикладной БД, без импорта старых системных таблиц `mysql.*`.

Глобальный SQL mode — `NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`; сессия PhpStorm дополнительно включает `IGNORE_SPACE`. Это не настройки PHP-сессии. `time_zone=SYSTEM`, MSK; `max_allowed_packet=16 MiB`; binary log выключен. Проверить эффективные настройки PHP и нового сервера. Не включать строгий режим одновременно с миграцией без теста старых обязательных полей `user` и фактических дат. NULL/дубликаты/даты и активные резервы нельзя доказать по схеме.

`persone.credit` и `history_balance.credit/credit_up` — FLOAT. Использовать существующий wallet rollout со снимком, проверкой точности и явной активацией DECIMAL(19,4); не заменять его прямым `ALTER` с округлением. Нужен `world-audit/credits`, а также `world-audit/data` для инвентаря. Структура не подтверждает сохранность кредитов, вещей, незавершённых игр и резервов.

### 6. Данные, блокирующие перенос кошелька

На полной копии штатный `world-audit/credits` обнаружил значения, которые текущий точный кошелёк не может принять без решения:

| Поле | Проверено строк | Требуют решения | Лишние десятичные знаки | Экспоненциальная запись |
| --- | ---: | ---: | ---: | ---: |
| `persone.credit` | 24 849 | 119 | 112 | 7 |
| `history_balance.credit` | 1 197 298 | 28 633 | 28 560 | 73 |
| `history_balance.credit_up` | 1 197 298 | 2 739 | 2 720 | 19 |

Отрицательных личных балансов и NULL в этих денежных полях нет. Экспоненциальные значения тоже требуют округления до 0,0001, поэтому простое расширение синтаксиса парсера проблему не решает. Диагностика основана на `CAST(FLOAT AS CHAR)` MariaDB и не восстанавливает точные суммы, существовавшие до записи во FLOAT.

Подготовлен только расчёт варианта `ROUND_HALF_UP` до 0,0001 Cr: для личных балансов изменились бы 119 значений, 72 вверх и 47 вниз; максимальное изменение одного значения — 0,00005 Cr, общий сдвиг около +0,000776224 Cr. Этот вариант **не применялся**. Перед реализацией нужно согласовать правило для остатков и отдельно для истории, сохранить исходные представления/значения, проверить реальные преобразования FLOAT→DECIMAL и зафиксировать разницу в отчёте переноса. Автоматически обнулять мелкие остатки или переписывать историю нельзя.

Ещё **6 строк `advertising` имеют отрицательный остаток**; стандартная проверка старых обязательств их отклоняет. Их происхождение и способ урегулирования нужно определить отдельно. Открытые позиции орла (39), дуэли (39), обмена (2 088) и перевода (1) проходят текущую проверку точности сумм/комиссий; это не подтверждение достаточности всех резервов и не основание отменять позиции.

До решения этих вопросов `wallet-snapshot/convert/activate` и полный допуск экономики не выполнены. `storage`/`accounts` rollout на всей пользовательской базе и конкурентные игровые сценарии остаются отдельной репетицией. Успех `world-setup/install` не скрывает эти блокеры.

### 7. Ложный отказ аудита на SQL-представлениях

Миграции объединения объектов создают шесть совместимых представлений: `world_bed`, `world_building`, `world_plot`, `world_region`, `world_room`, `world_settlement`. У VIEW в `information_schema.TABLES` нет движка. `WorldSchemaAudit` и `WalletCompatibility` принимали `ENGINE=NULL` за нетранзакционную таблицу; это давало ложные ошибки схемы и блокировало перенос кошелька даже после подготовки настоящих таблиц.

Обе проверки теперь различают `TABLE_TYPE`: представления не требуют отдельного InnoDB, их физический источник `world_node` проверяется. Обязательные старые финансовые таблицы и `advertising` по-прежнему должны быть физическими InnoDB-таблицами. В отчёт схемы добавлен `table_type`. Регрессия на MariaDB 10.1.48 проверяет шесть реальных VIEW, дополнительное тестовое VIEW и физическую MyISAM-таблицу: ложных отказов нет, MyISAM остаётся заблокированным. PHP 8.3.36 lint двух изменённых файлов прошёл.

## Репетиция на полном дампе MariaDB 10.1.48

Отдельный локальный сервер, только loopback `127.0.0.1:33319`; данные и журналы — `../temp/production-full-rehearsal-20261031/` относительно backend. Рабочее приложение, его подключение и production не изменялись. После проверки сервер остановлен.

Воспроизведены Antelope, `innodb_large_prefix=OFF`, `innodb_strict_mode=OFF`, page size 16384, utf8mb4/general_ci, non-strict SQL mode, max packet 16 MiB и MSK-смещение. Отличие: Windows использует `lower_case_table_names=1`, production Linux — 0. Это ограничение и поведение файловой системы требуют завершающего Linux-прогона.

1. Дамп восстановлен без ошибок: первый импорт около 40 секунд, повторный — 39 секунд на локальной машине. Это не оценка длительности production-окна.
2. До исправления движков установщик отказался из-за двух MyISAM-историй, не изменив список таблиц и историю миграций.
3. После `history_balance/history_rating → InnoDB` совпали количество строк и контрольные суммы содержимого **всех 64 исходных таблиц**, рассчитанные по всем значениям строк без вывода пользовательских данных.
4. Первый запуск остановился на `ALTER world_node ADD map_height` с локальным `errno 13 Permission denied`; повтор сообщил `1932 ... doesn't exist in engine`. Таблицы/служебные файлы вручную не исправлялись, этот экземпляр схемы сохранён для диагностики. Причина файлового отказа не установлена; успешное возобновление этого повреждения не заявляется.
5. На заново восстановленной базе штатный `world-setup/install` завершил **59 миграций + seed за ~67 секунд**. История выросла с 46 до 105 записей; все прежние записи сохранены. Схема 44, `world_read/world_write/storage_v2/economy_tick = 0`.

Количество категорий 5→7, предметов 45→53, рецептов 35→40; это изменение справочников, а не выдача вещей игрокам.

Контрольные суммы строк, определения индексов и столбцов сохранены. Суммарно перестройка заняла около 25 секунд локально; на production время и свободное место измеряются отдельно.

## Последовательность с учётом горячего выпуска

1. Завершить локальную репетицию точного кошелька, storage и accounts; сохранить исходники сумм, контрольные суммы, checkpoints и результаты повторов. Никаких тестовых кредитов или `test-ready` на production.
2. Подготовить отдельный переход с работающими писателями. Текущий freeze/snapshot/convert для этого не подходит. Нужны совместимый первый выпуск, обработка новых/изменённых строк во время копирования и атомарное переключение с проверкой. Проверить старые и новые процессы, регистрацию, cron, игры, подарки и worker; определить допустимые блокировки DDL. Не подменять этот этап простым `LOCK=NONE` — сервер уже отказал.
3. Отрепетировать InnoDB-конверсии и перенос на Linux/MariaDB 10.1.48 с параллельными начислениями, списаниями, историей и регистрацией. Отдельно проверить потерю соединения и повтор. Публичные данные и деньги не должны теряться между снимком и переключением.
4. Получить полный CI точного SHA. Восстановить доступ к GitHub Actions. Подготовить production workflow, который проверяет фактический результат установки мира; текущий `make up` и старый entrypoint не являются такой проверкой.
5. При успешных проверках выполнить разрешённую владельцем выкладку через GitHub Actions, без нового финального dump и без повторного запроса разрешения на тот же выпуск. При технической ошибке остановить следующие фазы и сохранить рабочую версию, не отключать проверки целостности.
6. После активации проверить версии схемы, точность денежных столбцов, миграции и флаги, состояние worker; наблюдать ошибки и блокировки. Старый дамп не восстанавливать поверх новых игровых операций автоматически: это потеряет последующие действия. Откат кода должен поддерживать новую схему; иначе требуется исправление вперёд.

Контрольный список: [план обновления](../plan/2026-10-31-production-schema-compatibility.md). Условное разрешение на production получено; условие успешной проверки горячего переноса ещё не выполнено.
