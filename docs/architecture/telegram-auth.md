# Вход через подтверждение в Telegram

Реализация от 4 ноября 2026. Основа — [auth-social.md](../tz/auth-social.md), сценарий уточнён владельцем: обычный чат с ботом, кнопка подтверждения, автоматический вход в исходной вкладке сайта. Mini App, Login Widget и обратная ссылка из чата для этого этапа не используются.

## Состояние на 6 ноября 2026

Сайт, API и отдельный бот реализованы. Бот работает на Node.js 26, приложение находится в `bot/project`. Настройка доступности хранится в `auth_provider_settings`; администратор с `p-admin` меняет её на `/auth-settings/index`. Миграция создаёт включённую настройку. Без общего ключа и подключённого бота вход остаётся недоступен.

## Сценарий

1. Вход/регистрация → «Войти через Telegram»: сразу создаётся заявка, в одном окне появляются код, ссылка в Telegram и таймер. Код и кнопка слева, пояснение справа; на мобильном пояснение открывается под иконкой. Для нового аккаунта пользователь явно разрешает его создание; изменение этого согласия отменяет старую заявку и создаёт новую. Игроку с существующим прогрессом предлагается сначала войти паролем и подключить Telegram в профиле.
2. Сайт создаёт заявку на 5 минут. В браузере показываются шестизначный код сравнения и ссылка `https://t.me/<bot>?start=login_<request_id>`.
3. После `/start` бот вызывает `bot/prepare`, связывая заявку с `message.from.id`. Бот показывает код, действие (вход либо привязка) и inline-кнопки подтверждения/отказа.
4. Только нажатие inline-кнопки вызывает `bot/confirm`. Открытие чата само по себе не подтверждает вход.
5. Исходная вкладка опрашивает API раз в 2 секунды. После подтверждения выполняет `complete`, получает обычный `{user, token}`, обновляет Vuex/хедер и переходит на исходный безопасный локальный адрес. В Telegram больше ничего открывать не требуется.
6. Для **привязки** сайт дополнительно показывает подтверждённый Telegram и просит нажать «Подключить». Это не даёт случайному получателю пересланной ссылки незаметно добавить способ входа к чужому аккаунту.

При возврате из мобильного приложения или перезагрузке страницы заявка восстанавливается из `sessionStorage` этой вкладки. Закрытие окна отменяет заявку; уход со страницы останавливает таймеры и запросы. Временный сетевой сбой автоматически повторяет опрос. Потерянный ответ завершения допускает короткий повтор с тем же доказательством.

## API браузера

Все пути относительно API сайта. JSON UTF-8. Ответы `Cache-Control: no-store, private`. Для привязки передаётся текущий `Authorization: Bearer <site-token>`; cookie сама по себе не разрешает привязку.

| Метод и путь | Тело / ответ |
| --- | --- |
| `GET /auth/telegram/config` | `{ "telegram": { "enabled": false } }`; секреты и адрес сервера бота не возвращаются. |
| `GET /auth/telegram/identity` | Требует входа. `{ "telegram": null }` либо `{ "telegram": { "provider": "telegram", "username": "name", "connected": true } }`. Telegram ID не публикуется. |
| `POST /auth/telegram/unlink` | Bearer сессия владельца и `{ "password": "пароль аккаунта" }` → `{ "telegram": null }`. Поддерживает старые и современные пароли, ничего не переписывает. Повтор безопасен. Доступен и при выключенном провайдере. |
| `POST /auth/telegram/start` | `{ "purpose": "login", "allow_signup": false }`. Для профиля `purpose: "link"`. |
| `POST /auth/telegram/status` | `{ "request_id": "…", "browser_secret": "…" }` → `{ "request": { "status": "pending", "expires_at": 1790000000, "telegram": null } }`. |
| `POST /auth/telegram/complete` | То же доказательство. Для входа — существующий `{user, token}`; для привязки — `{ "linked": true }`. |
| `POST /auth/telegram/cancel` | То же доказательство; отменяет `pending`/`approved`, повтор безопасен. |

Ответ `start`:

```json
{
  "request": {
    "id": "43-character-base64url-random-request-id",
    "browser_secret": "different-43-character-base64url-secret",
    "status": "pending",
    "display_code": "123456",
    "expires_at": 1790000000,
    "poll_after_ms": 2000,
    "telegram_url": "https://t.me/YourBot?start=login_REQUEST_ID"
  }
}
```

Строки выше — обозначения, не готовые токены. Реальные `id` и `browser_secret` имеют длину 43 и генерируются независимо из 32 случайных байт. Код из 6 цифр нужен **только для сравнения**, его нельзя использовать для входа.

Статусы: `pending → approved → completed`, либо `denied`/`cancelled`/`expired`. В `approved` браузер получает только `telegram.username` (может отсутствовать). `status` никогда не выдаёт сессию.

## Контракт отдельного бота

Ручки бота доступны только с `Authorization: Bearer <TELEGRAM_AUTH_API_KEY>`, по HTTPS вне development. Этот ключ отличается от BotFather token. По желанию дополнительно ограничивается исходящий IP бота.

`POST /auth/telegram/bot/prepare`:

```json
{
  "request_id": "REQUEST_ID_FROM_START",
  "telegram_user_id": "1234567890123",
  "telegram_username": "optional_username"
}
```

Ответ: `{request: {id, purpose, display_code, expires_at, status}}`. `telegram_user_id` — строка с положительным десятичным ID, до 16 цифр; `telegram_username` необязателен и может быть `null`. ID берётся только из настоящего Telegram update, не из текста сообщения или callback data. Первая подготовка закрепляет получателя, другой пользователь получает 409.

`POST /auth/telegram/bot/confirm`:

```json
{
  "request_id": "REQUEST_ID_FROM_CALLBACK",
  "telegram_user_id": "1234567890123",
  "approve": true
}
```

`approve: false` означает отказ. Ответ `{request: {status: "approved"}}` либо `denied`; повтор после успешного входа может вернуть `completed`. Сайт не выдаёт боту токен, профиль или браузерный секрет.

Действия бота:

- Использовать `getUpdates` с сохранением `offset`, обрабатывать только приватные чаты и живых пользователей (`is_bot=false`). На `/start` проверить `chat.id === from.id`.
- Проверять формат `login_` + 43 символа; произвольный текст и чужие ссылки не считать заявкой.
- После `prepare` отправлять отдельное сообщение с кодом, названием/доменом сайта и понятным действием. Для привязки явно писать, что пользователь добавляет способ входа к аккаунту сайта. Предупреждать не подтверждать чужие запросы.
- Использовать `callback_data`, например `ok:<request_id>` / `no:<request_id>`; обе строки укладываются в лимит 64 байта. Не использовать URL-кнопку для подтверждения.
- На callback проверять `callback_query.from.id`, приватный `message.chat.id` и соответствие сохранённому получателю; не доверять одному callback data. Отправлять API именно этот ID.
- Всегда завершать `answerCallbackQuery`, обновлять сообщение/убирать клавиатуру после ответа. При повторной доставке update не создавать новую заявку.
- Не писать BotFather token, общий API-ключ, полные `/start` ссылки, `Authorization` и browser secret в логи. При ошибке сети можно повторить тот же prepare/confirm; 401/403 — ошибка конфигурации, 409/410 — заявка закрыта, 429 — повтор с задержкой.

Официальные контракты: [deep links](https://core.telegram.org/bots/features#deep-linking), [getUpdates](https://core.telegram.org/bots/api#getupdates), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery).

## Конфигурация и размещение

В backend env нужен только `TELEGRAM_AUTH_API_KEY` — общий секрет не короче 32 символов. В боте ровно три параметра: `TELEGRAM_BOT_TOKEN`, `ABL_API_BASE_URL`, `TELEGRAM_AUTH_API_KEY`. Токен BotFather в backend не передаётся. TTL заявки — 300 секунд в коде. Старые env-переключатели и имя бота из env больше не читаются.

При запуске бот вызывает getMe, затем `POST /auth/telegram/bot/register` с `{bot_id: "12345", bot_username: "ExampleBot"}` и общим Bearer-ключом. API сохраняет публичные данные в настройках и возвращает `{bot: {registered: true}, site: {name: "Аблакин", host: "ablakin.ru"}}`. Для development возвращается `localhost:5173`. Регистрация разрешена при выключенном переключателе, но никогда его не включает. Без ключа или с неверным ключом регистрация запрещена.

Локальный endpoint бота в Docker: `http://host.docker.internal:3180`. HTTP разрешён только для локальных адресов; для внешнего API нужен HTTPS. Прямое подключение без Docker использует `http://127.0.0.1:3180`.

Применить миграции `m261104_120000_telegram_auth`, `m261106_120000_telegram_settings` и `m261106_140000_telegram_unlink`, указать общий ключ, запустить бота. Последнюю миграцию применять до обновления кода API отвязки; она добавляет два поля, не меняя существующих привязок. Имя бота вводить вручную не нужно. Переключатель и подключённое имя видны в админке «Настройки авторизации». Секреты интерфейсу не передаются.

На production ключ добавляется в `/var/www/api.ablakin.ru/.env`:

```dotenv
TELEGRAM_AUTH_API_KEY=<тот же общий секрет, что на сервере бота>
```

Не создавайте новый ключ отдельно от бота и не помещайте сюда `TELEGRAM_BOT_TOKEN`. IP сервера бота, его имя и env-переключатель не требуются. После изменения `.env` выполнить из каталога backend `docker-compose up -d --no-deps php`: простой `restart` не перечитывает окружение контейнера.

Workflow test/production запускает `php yii telegram-auth/install` с явным контекстом `TELEGRAM_AUTH_INSTALL=confirmed-test-checkout` либо `confirmed-production-checkout`. Команда применяет только три перечисленные миграции через штатную историю Yii, повторный запуск безопасен. Старые несвязанные миграции не запускаются. После установки workflow обновляет существующий crontab, чтобы включить очистку просроченных заявок. До первого запуска бота `GET /auth/telegram/config` может возвращать `enabled: false`: сначала бот должен зарегистрировать своё имя через API.

В каталоге bot запуск: `docker compose up -d --build`. Код и npm manifest/lock находятся в project, служебные файлы — в корне. Текущий push публикует исходники/образ; запуск на VPS выполняется отдельным ручным workflow. Production пока не выкатывается.

## Данные и безопасность

- `auth_identity`: уникальны `(provider, subject)` и `(provider, user_id)`. Внешняя идентичность — Telegram numeric ID, не изменяемый username. Удаление пользователя каскадно удаляет привязку в MySQL/PostgreSQL.
- Отвязка очищает владельца и username, увеличивает `auth_identity.revision`, записывает один `telegram.unlink` в аудит. Подготовка сообщения фиксирует эту версию в `telegram_auth_request.identity_revision`; завершение и повтор готовой заявки проверяют её под блокировкой. Старое подтверждение не восстанавливает удалённую привязку. Строка идентичности остаётся для отзыва старых заявок. Порядок блокировок: заявка → идентичность → пользователь; отвязка не блокирует заявки. Пароль подтверждает наличие альтернативного входа; Telegram-only аккаунту сначала нужен вход по паролю. Профиль, игровые данные, деньги и действующая сессия не меняются.
- `telegram_auth_request`: хранит только SHA-256 браузерного секрета; секрет не попадает в Telegram или URL. Для привязки фиксируется хэш исходного `auth_key`; смена/отзыв сессии запрещает её завершение.
- Подтверждение не создаёт аккаунт. Создание/привязка/аудит происходят при `complete` в одной транзакции. Блокируются заявка, внешняя идентичность, затем аккаунт. Уникальные ограничения защищают от параллельной регистрации.
- Новые пользователи создаются стандартным lifecycle Dektrium/User, включая `profile` и `persone`; повторной выдачи стартовых средств здесь нет. Username — `player_<случайный суффикс>`, пароль случайный и не раскрывается. Telegram не сообщает email: миграция разрешает `NULL`, не выдумывает адрес и не затрагивает существующие email/password/hash.
- Повтор `complete` разрешён 60 секунд и только пока токен аккаунта совпадает; logout/rotation отменяют восстановление. Блокировка пользователя запрещает вход. Текущая общая модель `auth_key` сохранена; отдельные device sessions и управление ими — другой этап исходного ТЗ.
- `auth_rate_limit`: общие для PHP workers минутные лимиты, 10 созданий/IP и 120 обращений/IP к каждой другой ручке. `auth_audit` хранит факт входа/привязки и user ID без секретов.
- `php yii telegram-auth/cleanup` удаляет старые заявки/счётчики и аудит старше 30 дней. Добавлен часовой запуск в Docker cron; для внешнего cron добавить команду отдельно.

Ошибки: 400 — неверное тело, 401 — нет нужной авторизации, 403 — чужая/заблокированная сессия, 404 — неизвестная заявка/неверный browser secret, 409 — конфликт или нет согласия на регистрацию, 410 — срок истёк, 429 — лимит, 503 — способ входа выключен. В frontend показывается сообщение API, а не внутренняя структура запроса.

## Локальная приёмка

Проверки жизненного цикла авторизации выполняются на изолированной БД. На локальную БД применяется миграция настроек, переключатель оставляется включённым. Реальный вход проверяется после заполнения BotFather token: новый аккаунт, существующий аккаунт, привязка, отказ, таймаут, возврат с телефона и повтор callback. Production — отдельный этап после этой проверки.
