# Журнал экономики и миграционный контракт MVP

Срез 2026-10-17, схема мира 39. Общий журнал читает существующие источники; повторного проведения денег или копии кошелька нет. Контракт — [economy-runtime-api.md](economy-runtime-api.md).

## Покрытие

| Действия | Источник факта | Связь эффектов |
| --- | --- | --- |
| Создание/получение/отмена существующего перевода | `history_balance`, `credit_transfer_history`; действующий `credit_transfer` | ID перевода и фаза; отменённый ID сохраняется после удаления перевода |
| Вступление, стартовые вещи, ежедневное снабжение | `game_operation`, `world_start_claim`, `world_supply_claim`, `inventory_movement` | Один ID операции; вступление не начисляет Cr |
| Исследование/покупка ячеек, строительство/отмена/ремонт, труд | `game_operation`, `game_command`, доменные журналы стройки/работ, `inventory_movement`, `economy_transfer` | Материалы, цена, резерв и выплата связаны операцией; отмена не создаёт вторую выдачу |
| Источники, шахта, ловушка | `world_source_work`, `world_economy_usage`, `inventory_movement` | Завершение партии хранит принятую ревизию; полный склад оставляет незавершённую доставку |
| Посев/полив/урожай | `world_crop_cycle`, `world_crop_revision`, `inventory_movement`, `economy_transfer` | Принятые условия культуры не заменяются текущим профилем |
| Крафт, использование, перемещение, еда | `game_operation`, `craft_command`, `inventory_movement`, `world_health_event` | Один ID для расхода/выхода; HP до/после — отдельный факт |
| Цели и продажа | `world_goal_pool`, `world_goal_claim`, `economy_order_fulfillment`, `economy_transfer` | Только зарезервированные деньги, один платёж и связанные вещи |
| Расширение хранения | `world_storage_expansion`, действующий журнал расширения, `history_balance`/`economy_transfer` | Вместимость до/после и цена фиксируются принятой командой |
| Казна, отчисления, потери | `economy_transfer`, receipts и история принятых финансовых правил | Потеря имеет отдельный счёт; сбор и внутреннее перемещение не считаются заработком |
| Административные изменения | `game_operation`, аудит объектов/каталога, профиль публикации | Автор и причина остаются в существующем аудите; денежный эффект — в том же ledger |

`commands` — журнал совершённых игровых операций, `credits` — движения счетов, `items` — движения вещей, `wallet` — существующий личный баланс, `transfers` — его переводные строки, `health` — HP. Разные строки одной операции нельзя суммировать как независимый заработок.

Новые команды сохраняют в `game_operation.context_json` только ID объекта и опубликованной ревизии, без произвольного payload. Для завершённой партии источника журнал берёт **принятую** ревизию `world_source_work`, включая получение после новой публикации. Снимки культуры, стройки, финансовой политики и резерва остаются в их доменных таблицах: номер текущего экономического профиля не заменяет эти условия.

Журнал возвращает `actor_user_id`, `node_id`, `profile_id`, `profile_version`, `from`, `to`, `item_id`, денежные остатки до/после и фактическое количество движения. Остаток до операции выводится точной десятичной арифметикой из сохранённого остатка после и движения. Для чужого счёта не выдаются его ID, объект или остаток. Доступ фильтруется до подсчёта страниц и totals. Владение проверяется на момент чтения.

У старых строк отсутствующие профиль/операция остаются `null`. Для прежних `Confirm #ID`/`Delete #ID` используется явный ID из комментария; для старой пакетной выдачи номера не угадываются по времени. Новые пакетные переводы получают отдельную связь для каждого ID. Связи записываются в той же транзакции, что деньги и история; FK на удаляемый `credit_transfer` намеренно отсутствует. Пароль перевода не читается журналом и не возвращается.

`quantity` — реальное движение, а не остаток стопки. История вещей не хранила снимки количества до/после; эти поля остаются `null`, включая новые движения через существующий canonical writer. Текущее содержимое склада не выдаётся за историческое. HP имеет достоверные `quantity_before`/`quantity_after`. Это явное ограничение read-контракта, а не основание перепроводить старые активы.

## Матрица установки и восстановления

| Состояние | Действие | Проверяемый результат |
| --- | --- | --- |
| Fresh install | Все world migrations до 39; seed; отдельный preview/publish | Таблицы и ограничения готовы; до публикации экономика выключена, денег и выдач нет |
| Upgrade существующей БД | Backup при остановленных writers; добавочная миграция 39 | Старые кошельки/вещи/команды сохранены; новые nullable поля пусты, профиль не активирован миграцией |
| Повтор | Повтор штатной команды установки и тестовой подготовки с теми же ключами | Нет второй публикации того же профиля, стартового перевода, резерва, заказа или цели |
| Частичный DDL MySQL | Повтор `up` после устранения исходной ошибки | Проверяются существование столбцов, таблиц, FK и unique отдельно; недостающие ограничения восстанавливаются, строки не удаляются |
| Ошибка прикладной транзакции | Повтор прежнего ключа после исправления | Квота/эффект/операция/идемпотентность откатываются вместе; при успешном commit replay возвращает исходный результат |
| Возврат цен | Preview исторического profile ID; публикация новой ревизии | Старый профиль и принятые условия сохраняются; возврат цен не возвращает деньги |
| Откат приложения | `world_write=0`, остановка worker, сверка; проверенная совместимая сборка | Схема 39 остаётся; отсутствующие nullable поля старый reader игнорирует. Старый writer без canonical `storage_id` запускать нельзя |
| Восстановление dump | Сначала отдельная БД, сверка всех таблиц/денег/резервов/вещей; затем остановленный стенд | Совпадение baseline; данные после времени backup обрабатываются отдельно, а не повторяются новыми ключами |

MySQL DDL имеет implicit commit: добавление схемы не объявляется атомарным с публикацией данных. `WorldMigration::up` использует существующий путь без внешней `safeUp`-транзакции на MySQL. `safeDown` доменных миграций не удаляет историю; рабочий способ отката — отключение записи и совместимое приложение/восстановление проверенной копии.

Подтверждения: fresh и upgrade проходят в release-наборах на MariaDB/PostgreSQL; в `world-economy-race.php` повтор частично удалённых FK/unique сохраняет строки. `world-economy-gameplay.php` проверяет корреляцию перевода и полный rollback при ошибке аудита. Полная копия локальной БД отдельно использована для подготовки нового участника, резервов 560 Cr и повторного запуска без изменения строк.
