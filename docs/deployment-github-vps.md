# Автодеплой backend из GitHub

Обновление предназначено для существующего checkout `/var/code/ablaki` на том же VPS, где работает `ablakin.ru`. Разработка ведётся в `master`. После push GitHub проверяет PHP 7.3, устанавливает зависимости из `yii2/composer.lock`, сохраняет проверенный vendor и запускает обновление по SSH. Повторный запуск доступен в Actions → Backend CI and production deploy → Run workflow, ветка master.

Служебные файлы хранятся в `/opt`, по той же схеме, что у frontend и PCM Helper:

| Назначение | Frontend | Backend |
| --- | --- | --- |
| Архивы, релизы и состояние деплоя | `/opt/ablaki-frontend` | `/opt/ablaki-backend` |
| Рабочие файлы приложения | `/var/www/ablakin.ru` | `/var/code/ablaki` |

Backend дополнительно хранит резервные копии БД в `/opt/ablaki-backend/backups`. Docker Compose запускается из существующего `/var/code/ablaki`, чтобы сохранить имя проекта, настройки и подключённые volumes.

## 1. Подключить доступ в backend-репозитории

В [Settings → Secrets and variables → Actions](https://github.com/fedornabilkin/ablaki/settings/secrets/actions) добавьте секреты. Можно использовать тот же VPS и уже разрешённый SSH-ключ, что у frontend, если этот пользователь имеет нужные права. Секреты двух репозиториев независимы: автоматически из frontend они не переносятся.

| Repository secret | Значение |
| --- | --- |
| `BACKEND_DEPLOY_HOST` | IP или DNS-имя VPS без протокола |
| `BACKEND_DEPLOY_PORT` | SSH-порт, например `22` |
| `BACKEND_DEPLOY_USER` | Пользователь, под которым доступны checkout и Docker |
| `BACKEND_DEPLOY_SSH_KEY` | Полный приватный ключ для этого пользователя; публичный ключ должен быть в его `authorized_keys` |
| `BACKEND_DEPLOY_KNOWN_HOSTS` | Запись SSH host key для этого хоста и порта, с отпечатком, проверенным через доверенное подключение к VPS |

В разделе Variables добавьте `BACKEND_HEALTHCHECK_URL`: полный адрес отдельного API-хоста с завершающим `/`, тот же, который указан в frontend `VITE_API_URL`. Это базовый URL, без `health` и без добавления `/api/`. Для сайта `https://ablakin.ru` API также должен работать через HTTPS.

Workflow использует environment `production-backend`. Секреты можно хранить в этом environment вместо repository secrets. Если для environment заданы ручное подтверждение или запрет ветки master, они будут учитываться GitHub; для полностью автоматического запуска настройте это согласно желаемому режиму.

Приватный ключ не нужно отправлять в чат или сохранять в репозиторий. Если исходный ключ frontend больше недоступен, GitHub не позволяет прочитать его обратно: создайте отдельную пару для backend и установите публичную часть на VPS.

## 2. Проверить существующий checkout

Один раз создайте служебный каталог под SSH-пользователя из `BACKEND_DEPLOY_USER`. В примере замените `deploy` его фактическим именем:

```bash
backend_deploy_user=deploy
sudo install -d -o "$backend_deploy_user" -g "$(id -gn "$backend_deploy_user")" -m 0700 \
  /opt/ablaki-backend \
  /opt/ablaki-backend/incoming \
  /opt/ablaki-backend/releases \
  /opt/ablaki-backend/backups
sudo -u "$backend_deploy_user" test -w /opt/ablaki-backend
```

Права `0700` ограничивают доступ к резервным копиям БД. Обычный workflow работает без sudo и ожидает, что каталог уже подготовлен.

Запускайте проверки под выбранным SSH-пользователем:

```bash
cd /var/code/ablaki
git branch --show-current
git status --short
git remote -v
git fetch origin master
docker compose version
docker compose ps
```

Поддерживается и старый `docker-compose`: если `docker compose version` недоступен, используйте его для последней команды. Ветка должна быть `master`, tracked-файлы — без локальных правок, origin — backend-репозиторий. Локальные правки нужно сначала сохранить и согласовать; скрипт их не стирает. `git fetch` должен работать без интерактивного запроса пароля.

Пользователю необходимы запись в `/opt/ablaki-backend`, checkout, `.git` и `yii2/vendor`, доступ к Docker без интерактивного sudo, а также `bash`, `make`, `curl`, `flock`, `tar`, `sha256sum` и обычные GNU coreutils. API runtime должен существовать и оставаться доступным PHP. Все команды Compose выполняются именно из `/var/code/ablaki`, с существующими `.env` и overrides; если проект запускали с особым именем, закрепите то же `COMPOSE_PROJECT_NAME` в серверной `.env`.

Автодеплой рассчитан на уже работающий сервис `postgres` из текущего Compose. Скрипт сверяет фактическую БД API и console с этим контейнером по идентификатору кластера, имени БД и префиксу таблиц. Для MySQL, внешней PostgreSQL или отдельного пользователя без права читать `pg_control_system()` сначала нужно адаптировать backup/проверку идентичности. При несовпадении текущая версия запускается обратно, код не обновляется.

Новые миграции форума и online, а также конкурентные операции следует проверить на отдельной копии целевой БД. Изолированные SQLite-проверки не подтверждают блокировки production PostgreSQL. Тесты workflow не подключаются к production.

## 3. Что происходит после push

1. CI проверяет синтаксис скриптов, сценарии ошибок деплоя и API-тесты на PHP 7.3, устанавливает production vendor из lock. Архив привязан к SHA коммита и хешу lock; хранится в GitHub 14 дней.
2. SSH передаёт архив в `/opt/ablaki-backend/incoming/<sha>`. На VPS проверяются контрольная сумма, состояние master и отсутствие другой публикации. Deploy-root и checkout должны быть отдельными каталогами; вложенные пути и архив вне ожидаемого incoming отклоняются до остановки API. Устаревший запуск пропускается, если master уже продвинулся дальше.
3. API, PHP/cron и старый composer-контейнер останавливаются. Проверяется, какая БД используется приложением. Создаётся PostgreSQL dump в custom-формате, проверяются завершение, размер, чтение каталога через `pg_restore --list` и SHA-256. Эта проверка архива не заменяет пробное восстановление на отдельной БД.
4. Checkout обновляется fast-forward до проверенного SHA. Предыдущий vendor сохраняется, новый устанавливается из CI. Совместимость расширений проверяется на серверном PHP; PHP-образ пересобирается при изменении Dockerfile/cron.
5. `make up` явно применяет миграции в режиме prod с выключенным debug и очищает кеш схемы, записывает SHA, затем пересоздаёт PHP и nginx. Cron запускается только после миграций. Сервис composer не запускается параллельно приложению. Console bootstrap по умолчанию также использует prod; локальную разработку можно включить через `YII_ENV=dev` и `YII_DEBUG=1`.
6. Проверяются внутренние JSON-контракты и внешний `GET <API_URL>health`. Успех требует HTTP 200, `status: "ok"`, нужный `revision` и `portalListsVersion: 1`. После этого сохраняется отметка успешной публикации.

На время backup и обновления API будет недоступен. Файлы `.env`, локальные настройки Yii, загруженные файлы и volumes остаются на сервере. `down --volumes`, сброс БД и `yii init` в этом процессе не используются.

Ручной `git pull`, затем `make up` остаётся доступен. Теперь `make up` также запускает миграции и пересоздаёт PHP/nginx. Он сам не создаёт backup и не устанавливает vendor: при ручном обновлении зависимости и резервную копию нужно подготовить отдельно. Не запускайте ручное обновление одновременно с Actions.

## 4. Первый запуск и связь с frontend

После добавления секретов и переменной запустите workflow на master. В Actions должны успешно завершиться обе задачи: Backend checks and dependencies и Deploy backend to production. Если первая публикация была запущена до настройки секретов, можно повторить упавшую deploy-задачу, пока её артефакт доступен.

Проверьте `GET <API_URL>health`: `revision` должен совпадать с SHA backend master. Затем повторите frontend workflow, если он ожидал API. Перед публикацией статики frontend теперь до трёх минут проверяет доступность совместимого API, JSON, CORS и отсутствие HTTPS → HTTP. При ошибке сайт остаётся на предыдущей версии. Изменение backend само по себе не запускает отдельный frontend-репозиторий.

После успешного обновления проверьте вход и чтение основных страниц. Проверки, изменяющие баланс или игры, выполняйте на предназначенном для этого тестовом окружении.

## 5. Ошибка и восстановление

Если ошибка произошла до изменения checkout/vendor, скрипт запускает прежние PHP/nginx. Если код или миграции уже изменены, API остаётся остановленным, чтобы не обслуживать запросы в частично обновлённом состоянии. Автоматического отката БД нет: он мог бы потерять данные или нарушить баланс.

Состояние находится вне web-root:

| Путь относительно `/opt/ablaki-backend` | Назначение |
| --- | --- |
| `backups/*.dump` и `.sha256` | Копия БД перед обновлением, доступна только SSH-пользователю |
| `releases/<sha>.<suffix>/previous-sha` | Предыдущий коммит |
| `releases/<sha>.<suffix>/previous-vendor` | Предыдущие зависимости |
| `current` | SHA последнего успешно проверенного деплоя |

Если прежняя версия скрипта уже создала копии в `/var/code/ablaki/.git/ablaki-deploy`, они сохраняются на прежнем месте. Новые публикации используют `/opt/ablaki-backend`; автоматического переноса или удаления прежних копий нет.

Сначала изучите ошибку Actions и логи контейнеров. Исправление вперёд новым коммитом обычно позволяет повторно применить только оставшиеся миграции. Откат кода и восстановление БД требуют отдельного решения с учётом уже выполненных миграций и операций. Проверяйте восстановление dump на отдельной БД, не поверх работающей production-БД для теста.

Скрипт не удаляет старые копии автоматически. Следите за свободным местом и храните копии вне VPS; удалять старые архивы можно только при отсутствии активного деплоя и наличии проверенной копии нужной версии.

## Проверка реализации

Проверки публикации включают 14 изолированных сценариев: успех с отдельным deploy-root, устаревший SHA, локальные изменения, неверную ветку, занятую блокировку, повреждённый архив, другую БД, сбой backup, миграций и healthcheck, deploy-root внутри checkout и над ним, отсутствующий deploy-root и архив вне incoming. Docker, SSH и production-БД в этих тестах заменены управляемыми заглушками. На PHP 7.3.33 и 8.3.33 с актуальным lock прошли 139 API-проверок и 9 проверок health. В worker-тестах учтены отдельное PDO-расширение Ubuntu и запуск процессов Windows PHP 7.3. GitHub дополнительно проверяет Linux/PHP 7.3.

Эта инструкция описывает подготовленную автоматизацию. Настройка SSH-секретов и первый серверный запуск требуют доступного подключения; их нельзя считать выполненными по результатам локальных тестов.

6 сентября [GitHub CI на Ubuntu/PHP 7.3](https://github.com/fedornabilkin/ablaki/actions/runs/34026282545) успешно проверил код и собрал артефакт. Серверная задача остановилась до SSH: не настроен `BACKEND_DEPLOY_HOST`. [Frontend CI](https://github.com/fedornabilkin/ablaki-front/actions/runs/34025943932) также успешно прошёл тесты и сборку; активация статики не выполнялась из-за таймаута запроса API health. После подключения доступа нужно подтвердить первый серверный запуск и доступность внешнего API для GitHub runner.
