# Неактивные пользователи

## Цель и принятое решение

Источник: тема 68, сообщение 195; уточнение владельца от 24.09.2026. Постоянно учитывать действия через `user.latest_activity` и снижать `persone.rating` у неактивных пользователей. Единый баланс — `persone.credit`.

- Первое снижение — после 180 полных суток с последней активности, последующие — не чаще чем через 30 суток после предыдущего прохода.
- Каждый проход снимает 10% текущего рейтинга с округлением результата до двух знаков; нижняя граница — 5. Рейтинг, который уже ниже 5, не меняется.
- Первый запуск не начисляет несколько штрафов за прошлые месяцы: один проход сейчас, следующий через 30 дней.
- После любого действия новый отсчёт 180 суток начинается от `user.latest_activity`. Вход — лишь один из видов активности.
- Каждое снижение записывается в `history_rating`: прежний и итоговый рейтинг восстанавливаются по `rating` и отрицательному `rating_up`; комментарий содержит причину и дату последней активности.

## Группа A: Постоянная активность

- [x] A1. Использовать существующую таблицу `user` и поле `latest_activity`, не создавать второй источник активности.
- [x] A2. Добавить безопасную миграцию для теста: nullable DATETIME, заполнение по более поздней дате регистрации/входа; при неизвестной дате — время миграции. Существующие значения production сохраняются. Выборочная команда `activity-setup/install` включена в workflow и применяет только эту миграцию, в том числе без пересоздания контейнера.
- [x] A3. Записывать активность на каждом авторизованном действии API, включая публичные страницы с корректным bearer-токеном, вход и страницы старого сайта/админки. Задержавшийся запрос не уменьшает время.
- [x] A4. Использовать поле для онлайн-списка, посещений за сегодня и последнего посещения в публичном профиле.

Храним формат legacy DATETIME без часового пояса, московское время; API отдаёт `latest_activity` Unix timestamp. Неизвестные/нулевые старые даты не дают оснований для штрафа. На тесте поле дополняется по известным датам; существующий production DATETIME не преобразуется и не перезаполняется.

## Группа B: Снижение рейтинга

- [x] B1. Выполнять выбранную политику через существующий ежедневный `cron/user-clear`; отдельный запуск доступен как `cron/inactive-rating`. Старое автоматическое удаление трёхдневных регистраций этим заданием заменено на обработку рейтинга.
- [x] B2. Обрабатывать пользователей порциями по ID; повторно проверять активность под блокировкой строки `user`, затем блокировать `persone`.
- [x] B3. Менять рейтинг, добавлять историю и сохранять `user.inactive_rating_at` в одной транзакции. Повторный или параллельный запуск не выполняет второй проход.
- [x] B4. Отсчитывать 180/30 дней, применять 10% к текущему рейтингу, соблюдать минимум 5; сохранять новый срок только после успешной записи истории.

## Группа C: Критерии готовности

- [x] C1. Проверить точные границы 180 и 30 суток, возвращение пользователя, нижнюю границу и комментарии истории.
- [x] C2. Автоматизировать повтор миграции, сохранение production-подобного DATETIME и откат при ошибке журнала; включить конкурентные сценарии MySQL/PostgreSQL в обязательный CI на изолированных БД.
- [x] C3. Проверить запись активности при действии, посещении публичной страницы с токеном и входе без изменения пароля, соли или auth_key.

## Группа D: Отложенные предложения из первоначального плана

Архивирование и удаление пустых регистраций требуют отдельного решения. Списание накопленных кредитов не выбрано владельцем. Следующие пункты остаются предложениями и не включены в ежедневную обработку:

- [ ] D1. Подготовить отчёт о пустых регистрациях: исправить старую проверку остатка `persone.credit`/`balance`, минимальной даты и защиты пригласителя через `refovod`.
- [ ] D2. Проверять зависимости игр, переводов, финансовых журналов, форума, рефералов и `craft_*`; при неизвестном состоянии исключать удаление.
- [ ] D3. Сделать административный список кандидатов с причинами, последней активностью и экспортом без приватных данных.
- [ ] D4. Определить обратимый архив и восстановление при возвращении; отдельно согласовать влияние архива на выдачу и призовой фонд.
- [ ] D5. После D1–D4 согласовать выключенный по умолчанию исполнитель удаления: период ожидания, блокировка, повторная проверка, обработка порциями, журнал и остановка.
- [ ] D6. Для удаления отдельно проверить гонки с активностью и экономическими операциями, сохранение авторства/аудита и восстановление архива; изучить отчёты до включения.
