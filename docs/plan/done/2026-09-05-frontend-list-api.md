# API для рабочих страниц SPA

Цель: дать SPA серверный поиск, воспроизводимые списки и существующие данные статистики, подсказок и пользователей.

Контекст: запрос пользователя от 2026-09-05. Игровые и форумные изменения выполняются параллельно в своих доменах. Старые клиенты сохраняют массивы; SPA явно запрашивает `envelope=1`. Работа с реальными аккаунтами и production-БД для тестов запрещена.

## Группа A: Общие списки
- [x] A1. Добавить общий ApiList с q, разрешёнными полями сортировки, ограниченной пагинацией и сортировкой новых записей первыми.
- [x] A2. Добавить opt-in сериализацию items/_meta с настоящими totalCount и pageCount.
- [x] A3. Подключить историю, биржу и переводы; сохранить ограничения владельца запросов.
- [x] A4. Исправить выбор модели balance/rating и вернуть типы истории текущего пользователя.

## Группа B: Общественные страницы

- [x] B2. Считать онлайн по отдельной активности за пять минут; сохранить значение последнего входа.
- [x] B3. Подключить случайную подсказку из существующей fact и пагинируемый рейтинг.

## Группа C: Проверки и выпуск
- [x] C1. Проверить списки, поисковые ограничения, owner-scope, metadata и activity на временной SQLite — 32 проверки, включая wiring маршрутов и сериализатора.
- [x] C2. Проверить синтаксис всех изменённых PHP и описать необходимые миграции — 15 файлов, PHP 8.3.33; `docs/frontend-list-api.md`.
- [x] C3. Выполнить независимый совместный аудит форума, игр и списков — 139 проверок в 6 suites, включая 58 full-dispatch проверок; lint всех 34 изменённых PHP. Последний повтор форума проверяет создание темы с view=0. `docs/frontend-api-integration-audit.md`.

Критерии готовности: запросы из URL дают те же списки/количество страниц; поиск применяется до COUNT/LIMIT; не раскрываются чужие балансы и секреты переводов; production-БД не затронута. Для активности и подарков обязательны миграции до выкладки API; SQLite не доказывает блокировки PostgreSQL/MySQL.
