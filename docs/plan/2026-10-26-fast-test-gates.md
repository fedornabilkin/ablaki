# Минимальные проверки перед test и полный прогон после публикации

Поручение 2026-10-26: новая версия должна становиться доступной на тестовом стенде после коротких необходимых проверок; остальные тесты запускаются после публикации. Цель — оперативные исправления без ручных пауз. Полные проверки production остаются обязательными до его выкладки.

## Группа A: Проверки

- [ ] A1. Оставить перед test backend синтаксис, lock/platform и короткие сценарии запуска/авторизации/основных операций; исключить запуск сервисов MySQL/PostgreSQL из минимального job.
- [ ] A2. Выполнять полные backend/MySQL/PostgreSQL проверки отдельным job после успешного test deploy; сохранить блокировку production полным прогоном.
- [ ] A3. Для test frontend оставить проверки транспорта/авторизации, окружения и сборку; полный клиентский прогон выполнять после публикации.

## Группа B: Публикация

- [ ] B1. Повторно использовать установленный мир при совпадении установочных файлов и подтверждённом состоянии БД; при pending/изменениях сохранять полный возобновляемый путь.
- [ ] B2. Встроить публикацию изменённого профиля в выпуск с проверкой автора и сохранности средств/вещей; сохранить изменения профиля администратора при неизменённом файле.
- [ ] B3. Исправить завершение worker после текущей работы и исключить лишние SSH-соединения при передаче frontend.
- [ ] B4. Подтверждать готовность коротким автоматическим smoke и точной версией; результат deploy доступен до окончания дополнительных тестов.

## Группа C: Проверка внедрения

- [ ] C1. Проверить отказ коротких проверок, готовый/неготовый мир, повтор, профиль и завершение worker изолированными сценариями.
- [ ] C2. Опубликовать изменения в test обоих репозиториев; измерить запуск минимального пути, повторную выкладку и независимый полный прогон.
- [ ] C3. Обновить инструкции и фактические измерения. Не считать максимум 120 секунд доказанным без серии измерений из общего плана оптимизации.
