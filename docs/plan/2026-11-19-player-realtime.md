# Живая лента мира и объектов, личные уведомления и чат

## Цель

Игрок, открывший шахту, видит строку «Пользователь demix добыл камень и железную руду», когда сервер зачислил оба ресурса. Владелец узнаёт о завершении своей стройки, даже если сейчас находится на другой странице. В ленту всего мира попадают редкие события, меняющие доступные игрокам действия. Обычная добыча остаётся в ленте соответствующего объекта.

Первый выпуск охватывает добычу, завершение стройки и доставку уже существующих личных уведомлений через SSE (поток событий от сервера к браузеру). WebSocket нужен для двустороннего общения в комнатах чата. Два направления можно выпускать по отдельности.

## Контекст

- Диспетчер читает `game_outbox`, а worker обрабатывает доставку каждому подписчику с защитой от повторов через `game_inbox`. Потребитель работает внутри транзакции задания. Игровое явление в `world_event`, доступное через `GET v1/world/events`, имеет собственный жизненный цикл. Для истории действий нужен отдельный ресурс. [План мира, A6/G7/J6](2026-09-26-world-backend.md) · [Архитектура событий](../architecture/world-events-characteristics.md) · [Outbox](../../yii2/common/modules/world/support/Outbox.php)
- Личные уведомления уже хранятся в `game_notification`. Сервер учитывает тип, настройку канала, владельца и отметку чтения. Для доставки в открытую вкладку ТЗ предусматривает `notification.created` с `notification_id` и `unread_count`. Раздел E6 клиентского плана мира предусматривает опрос только на видимой странице. [WorldNotifications](../../yii2/common/modules/world/models/domain/WorldNotifications.php) · [ТЗ уведомлений, §13](../tz/notification.md)
- Во frontend есть адаптер `project/src/services/chat/socket.js` и режим `mock`. План чата предусматривает REST-историю, авторизацию комнат и WebSocket-брокер, среди вариантов — Centrifugo. Сервер чата числится отложенной работой. Группа E ниже использует тот же план и адаптер. [План backend чата](2026-10-29-chat-backend.md) · [ТЗ чата](../tz/chat.md)

Отбор местных событий по положению персонажа, их группировка по своей и соседним стоянкам и сводка за время отсутствия описаны в [плане самостоятельной жизни мира](2026-11-19-autonomous-world.md).

## Какие события увидит игрок

| Где | Повод | Что показываем | Когда доставляем |
|---|---|---|---|
| Открытая карточка объекта | Игроку зачислена партия добычи | «Пользователь demix добыл камень и железную руду». Одна строка на партию, даже если ресурсов несколько | SSE после фиксации выдачи, только тем, кто вправе видеть активность объекта |
| Карточка объекта и личный раздел | Постройка готова | У объекта «Завершено строительство кузницы». Получателю личного уведомления — «Постройка готова к использованию» | SSE в ленту объекта и сигнал о сохранённом личном уведомлении. В общей ленте отдельное сообщение только для открытия общественного объекта |
| Лента мира | Открылся общедоступный объект или началось игровое явление, затрагивающее участников мира | Например, «В Северограде открылась кузница». Ссылка ведёт к доступному объекту | Следующий выпуск. Объявление после изменения доступности, один раз на переход состояния |
| Личный раздел | Завершено производство, собран урожай, получена награда | Изменение счётчика и запись в существующем списке. Суммы и состав инвентаря доступны только через соответствующие личные экраны | SSE адресату после сохранения уведомления. Остальные типы включать по мере появления проверенных источников |
| Чат | Сообщение в комнате, собеседник печатает | Содержимое или краткий индикатор участникам комнаты | WebSocket. Историю сообщений восстанавливаем по REST, индикатор набора истекает и не воспроизводится |

Таймеры в браузере, каждый heartbeat добычи, предварительный расчёт и процент стройки не порождают строки ленты. Серверные команды начала/продолжения работы остаются в HTTP API с действующей проверкой прав и идемпотентности. Отказ склада показывается исполнителю через результат операции. Записи об успешной добыче в этом случае нет.

## Группа A: Контракт и аудитория

- [ ] A1. Для строк таблицы закрепить в контракте мира тип, производителя, момент фиксации, адресата и поля, доступные этой аудитории. Первый срез — личная партия добычи на источнике и завершённая стройка. Для общественной стройки определить серверный признак публикации в мире.
- [ ] A2. После A1 описать версию сообщения, стабильный ID события, время сервера, тип, контекст мира/объекта и типизированные параметры текста. Для добычи передавать исполнителя и массив реально выданных позиций с количеством. Отдельно задать курсор доставки. Обновить спецификацию REST-истории, примеры SSE и коллекцию Insomnia при реализации API.
- [ ] A3. После A1 описать решения о доступе для участника мира, наблюдателя объекта и адресата личного сообщения. Права проверять на сервере при подписке, воспроизведении истории и последующей доставке. При смене владельца, отзыве прав или выходе из аккаунта прекращать доступ, в том числе к буферу ожидающих событий.

## Группа B: Подтверждённые факты и история

- [ ] B1. После A2 фиксировать факт выдачи в той же транзакции, что переводит `world_source_work` в `completed`. Использовать исполнителя партии и её собственный идентификатор выдачи. Один checkpoint может завершить работы нескольких людей. Для коллективной шахты, где известны только общий выпуск и склад владельца, использовать безличный текст «В шахте добыт камень». Проверить полный склад, откат и повторную обработку. [WorldSources](../../yii2/common/modules/world/models/domain/WorldSources.php) · [Mining](../../yii2/common/modules/world/models/Mining.php)
- [ ] B2. После B1 подключить отдельного потребителя к исходному `world.construction.finished` и новому факту добычи. В транзакции доставки сохранять строку истории один раз по исходному ID и области видимости. Внешнюю отправку выполнять после commit. Повтор после сбоя публикации восстанавливает доставку уже существующей строки.
- [ ] B3. После A3/B2 добавить постраничную историю действий объекта и мира. Первая страница и курсор продолжения представляют один согласованный срез. Проверить, что курсор учитывает порядок фиксации записей, когда две параллельные транзакции завершаются в обратном порядке. Срок хранения истории и окно повтора потока задать отдельно.
- [ ] B4. После A2/A3 выпускать приватный `notification.created` по сохранённой записи `game_notification`. Использовать действующие REST-методы списка, отметки прочитанного и настроек. Выключенная категория не даёт сигнал, получение SSE не помечает запись прочитанной. В тихие часы уведомление по-прежнему видно внутри сайта, как предусмотрено настройкой канала in_app.
- [ ] B5. После F4 подключить публичные объявления мира из таблицы. Проверить, что каждое публичное открытие создаёт одно объявление, а закрытая постройка остаётся видна только своей аудитории.

## Группа C: Доставка SSE

- [ ] C1. После A2/A3 поднять на стенде отдельный процесс доставки за nginx. Yii продолжает обслуживать короткие API-запросы. На пути до браузера проверить `text/event-stream`, отключение буферизации/кэширования, heartbeat и таймаут простоя. Сверить возможность общего брокера с планом чата, отдельно измерить потребность в Redis.
- [ ] C2. После C1 и B3 реализовать подписку вкладки на личный поток и выбранную область мира или объекта. Сервер определяет пользователя по действующим учётным данным и проверяет его права на запрошенную область. Для SPA с Bearer-заголовком использовать streaming fetch с отменой запроса и существующим источником авторизации. При смене области передавать свой курсор для каждой подписки.
- [ ] C3. После B2–B4/C2 обеспечить переход от истории к потоку без пропуска между чтением и подпиской. При обрыве клиент передаёт последний обработанный курсор, сервер воспроизводит доступные записи и продолжает live-доставку. При истечении окна повтора клиент получает явный сигнал заново загрузить историю и счётчик. Доставка допускает повтор одного ID.
- [ ] C4. После C3 ограничить очередь медленного клиента и число подписок. При переполнении закрывать поток с восстановлением по курсору. При недоступности транспорта оставить рабочими игровые команды и историю. При переезде на PostgreSQL проверить сохранение ID и восстановление по старому курсору, чтобы история не появилась в ленте как новые события.

## Группа D: Интерфейс игрока в ablaki-front

- [ ] D1. После A2/C2 добавить общий подписчик с проверкой схемы сообщения, отменой при выходе и повторным подключением с увеличивающейся задержкой. При смене персонажа/аккаунта очищать строки и курсоры предыдущей сессии. При переходе между объектами отбрасывать запоздалый ответ старой подписки.
- [ ] D2. После B3/D1 добавить текстовый журнал в карточку объекта и ленту мира с временем и ссылкой при наличии доступа. Показать историю при первом открытии, добавлять новые строки один раз по ID, имена и названия выводить обычным текстом. Не сбивать прокрутку при чтении истории. На смартфоне длинная строка добычи должна помещаться без горизонтальной прокрутки.
- [ ] D3. После B4/D1 обновлять личный счётчик и список, дать прочитать запись и изменить предпочтения. Обычная добыча соседа остаётся строкой объекта. Личный результат, уже показанный в активной карточке, не вызывает второе всплывающее сообщение.
- [ ] D4. После C3/D1 при потере SSE включать резервный опрос видимой страницы раз в 30–60 секунд и при восстановлении сверять её с сервером. В `SimpleBuildPanel.vue` сократить фоновые чтения только после замеров. В `WorldMiningPanel.vue` сохранить heartbeat, которым сервер учитывает работу игрока.

## Группа E: Двусторонний чат по WebSocket

- [ ] E1. В рамках действующего плана чата согласовать рабочий протокол frontend-адаптера и брокера на стенде. Проверить выдачу короткоживущих полномочий на комнату, TLS, Origin, отзыв членства и очистку очереди старой сессии. Долгоживущий API-токен исключить из URL и логов. Вход игрока в мир не требует открытия сокета чата.
- [ ] E2. После E1 и появления серверной истории чата провести обмен между двумя участниками. Подтверждённое сообщение сохраняется один раз при повторе после обрыва, пропущенное приходит из истории. Индикатор набора исчезает по таймауту. Проверить запрет доступа третьему игроку в закрытую комнату на реальном транспорте.

## Группа F: Приёмка и включение

- [ ] F1. После B1–B4/C3/D2–D3 воспроизвести на тестовой БД сценарий трёх игроков. demix получает камень и руду, наблюдатель шахты видит одну строку, игрок без доступа не видит её ни в SSE, ни через историю. Переподключить наблюдателя во время второй выдачи. Проверить отсутствие пропусков и дублей, верное имя для каждой выдачи двум работникам и отсутствие сообщения при откате транзакции. Отозвать доступ у наблюдателя с открытой карточкой. Следующая выдача должна быть скрыта при работающем соединении и после переподключения.
- [ ] F2. После C4/D4 измерить на стенде время от commit до показа в видимой вкладке при обычной и пиковой нагрузке. Начальная цель для первого выпуска — p95 до 10 секунд, с учётом нынешней пятисекундной паузы цикла worker. Записать задержку очереди, соединения, число повторных чтений, расход памяти и влияние на обычное API. Проверить рестарт worker/шлюза и переподключение группы клиентов. [Цикл worker](../../yii2/console/world-worker-loop.sh)
- [ ] F3. После B4/C3/D3 завершить стройку, пока её владелец находится на другой странице. У владельца с включённой категорией появляется одна непрочитанная запись, у постороннего личный счётчик не меняется. Повторить с выключенной категорией и проверить отсутствие личного сигнала.
- [ ] F4. После F1/F2/F3 включить SSE на тестовом мире, затем по отдельным флагам для ленты и личных уведомлений. Выключить флаг во время игры и проверить возврат клиента к REST, доступность истории и выполнение команд старым клиентом. Чат включать отдельно после E2.

## Группа G: Колокольчик в общей шапке сайта

Цель — дать вошедшему пользователю единый личный центр на любой странице. В мире уже есть список по 20 записей, общий счётчик в ответе, чтение одной записи и настройки. Центру по ТЗ нужны порции по 30, отдельный лёгкий запрос счётчика, массовое чтение и переход к источнику. Первую версию интерфейса можно принять на REST. [ТЗ колокольчика, §3–13 и §17](../tz/notification.md) · [Действующий API](../../yii2/common/modules/world/apiControllers/NotificationController.php)

- [ ] G1. Описать общесайтовый контракт поверх сохранённых личных уведомлений. Сопоставить тип, категорию, время, текст и внутреннюю цель перехода. Старые записи без ссылки должны открываться и читаться. Сохранить прежний формат `v1/world/notifications` и проверить работу центра у пользователя без персонажа.
- [ ] G2. После G1 реализовать список с устойчивым курсором по 30 записей и отдельный `unread-count`. Счётчик относится ко всем непрочитанным записям владельца. Между первой и второй порциями вставить новое уведомление и проверить отсутствие пропусков и дублей.
- [ ] G3. После G1 дополнить существующее чтение одной записи операцией «Прочитать все». В одной транзакции отметить записи владельца до границы операции и вернуть серверные счётчики. Повтор с тем же ключом сохраняет результат. Запись, созданная после этой границы, остаётся непрочитанной.
- [ ] G4. После G2/G3 добавить колокольчик в правую часть общей шапки. При нуле скрывать бейдж, от 1 до 99 показывать число, при 100 и выше — «99+». В панели вывести категорию, дату, текст, «Прочитать», «Прочитать все» и «Показать ещё 30». Открытие панели сохраняет статус записей. Клик по карточке отмечает её прочитанной, затем открывает разрешённую цель при её наличии. На мобильном использовать адаптивную панель, поддержать Escape и возврат фокуса на кнопку.
- [ ] G5. После G1 подключать производителей по подтверждённым событиям. Повтор доставки даёт одну запись адресату. Для достижений использовать `ACHIEVEMENT_UNLOCKED`, для мира — существующие события и настройки. Зафиксировать правила хранения и лимитов из §14 ТЗ с отдельной политикой для важных записей. Цель перехода разрешается на сервере с учётом текущих прав.
- [ ] G6. После G4/G5 проверить гостя, два аккаунта, две вкладки, 0/1/99/100 непрочитанных, 31-ю запись, одновременное массовое чтение и новую доставку. Проверить пустое состояние, недоступный объект и сетевой повтор. После B4/C3/D3 сверять тот же бейдж по SSE и при восстановлении связи по REST. Обновить спецификацию API и Insomnia.

## Критерии готовности

Первый выпуск принят, когда наблюдатель видит корректный результат выдачи в карточке без обновления страницы, владелец получает личное уведомление о стройке, а проверки прав, восстановления связи и личной доставки проходят по F1/F3. Замер F2 подтверждает согласованный срок доставки, проверка F4 — работоспособность при отключённом потоке. Для общих объявлений мира дополнительно требуется B5, для чата — E2. Реализация и замеры предстоят. Колокольчик принимается по G6 на desktop и мобильном экране. Его счётчик и состояния чтения сохраняются после перезагрузки.
