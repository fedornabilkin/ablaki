# Договоры ремонта для прежних покупок — D18

Дата: 2026-09-27. Код подготовлен в `feature/09-worlds`, не опубликован. Миграция 200000 и schema marker 20. Тесты, сборка, миграция и игровая приёмка не запускались.

## Публикация и принятие

В существующем каталоге построек Yii-админки при публикации задать цену/сырьё полного ремонта и включить «Предлагать договор владельцам ранее купленных зданий». Требуются обычные маршрутные права редактора предложений; отдельная роль в коде не добавляется. По умолчанию флажок выключен. Только явно опубликованные с ним предложения появляются в списке договоров.

Владелец прежней покупки открывает свою постройку `/world/nodes/{id}`, раздел «Договор ремонта». Список содержит только действующие предложения исходного поселения, совпадающие с первоначальной покупкой по типу (`canopy/workroom/house`) и площади. Поиск по названию и страницы по 20 записей выполняются сервером; фильтрация происходит до подсчёта. Последние предложения сверху, параметры сохраняются в URL.

Принятие бесплатно. Preview показывает подрядчика, цену полного ремонта и нормы сырья. Принятие не ремонтирует здание, не расходует бюджет/личные Cr/вещи, не покупает новое помещение и не занимает площадь. После подтверждения договор появляется в карточке здания; фактический ремонт выполняется прежней отдельной командой с оплатой из бюджета здания в казну первоначального поселения. Требования к покупателю нового здания не являются условиями принятия ремонтного договора: здесь приобретается обслуживание уже принадлежащего игроку объекта, а не новая постройка.

Цена и материалы закрепляются в отдельном неизменном дополнении к покупке. Снятие предложения с продажи закрывает новые принятия, но сохраняет уже принятые договоры. Цена новой покупки из этого же предложения не списывается при подписании. Владельцу нельзя заменить договор, который уже был включён в покупку или принят отдельно. Автоматического выбора тарифа и массового назначения старым зданиям нет.

## БД и интеграция

Миграция `m260927_200000_world_repair_contract` добавляет две таблицы:

- `world_repair_offer`: индекс явно разрешённых предложений по типу/площади с FK на существующее предложение; жизненный цикл публикации/снятия остаётся у `world_premises_offer`.
- `world_repair_contract`: отдельный принятый снимок с FK на здание, покупку, предложение, владельца и операцию. UNIQUE здания/покупки/операции предотвращают второй договор. `terms_json` первоначальной покупки не переписывается.

Таблица индекса заполняется только при новой явной публикации, в одной транзакции с предложением. Предыдущие публикации без флажка не становятся предложениями для старых зданий задним числом. Для них можно создать новое предложение с нужными условиями.

Миграция использует `WorldMigration`: создание таблиц/индексов/FK возобновляемо, типы внешних ключей берутся из фактической схемы. На MySQL/MariaDB нет внешней safeUp-транзакции вокруг DDL. Данные не переносятся и не удаляются. `world-setup/install` устанавливает marker 20 только после успешного выполнения всех миграций и seed; до этого новая версия мира закрыта через schema_ready. Миграция ещё не применена ни в test, ни в production.

`WorldRepairContracts::effective()` выбирает договор исходной покупки либо принятое дополнение. Ремонт использует этот снимок, а preview фиксирует `repair_contract_id` и `repair_template_revision_id` дополнительно к исходной версии покупки. Списание сырья, тариф, финансовые правила, ночлег и состояния здания остаются в `WorldBuildingRepair`. Обычный CRUD защищает здание со связанным договором от изменения владения/структуры/архивации.

## Доступ и ограничения

Принимает только фактический владелец купленного здания. Административные полномочия мира не дают права принять договор за другого игрока. Сохраняются проверки жизненного цикла: шалаш, действующая стройка, разрушенное/архивное здание и неподдерживаемые вложенные объекты исключены.

В этом этапе исходная покупка должна иметь одну собственную активную комнату с прежней площадью и прежнюю площадку-родителя. Поселение-подрядчик и его предки должны быть активны. Неисправные материалы действующего каталога блокируют принятие, но предложение остаётся видимым с причиной. Отсутствие сырья в рюкзаке и денег в бюджете не мешает принять бесплатный договор — достаточность проверяется при ремонте.

Принятие использует CommandBus: locks в установленном порядке, действующий quote/revisions, повторная проверка публикации и отсутствия договора перед INSERT, аудит и outbox атомарно. Повтор потерянного ответа возвращает прежний результат без второго договора. Гонка двух разных предложений завершается одним принятием; последующее требует уже недоступной замены. SPA сохраняет незавершённую команду и отбрасывает устаревшие ответы/ответы прежнего аккаунта.

Здания из CRUD без записи покупки, сложные перестроенные объекты, смена подрядчика и переоформление уже действующего договора остаются будущими сценариями. Историческую покупку нельзя править вручную ради обхода этих ограничений.

## Контракты и приёмка

[OpenAPI договоров](../../api/world-repair-contracts.openapi.json), [предложения v1.5](../../api/world-premises.openapi.json), [ремонт v1.1](../../api/world-building-repair.openapi.json). GET `repair-contracts`, POST `repair-contract-preview`, POST `repair-contract` под `/v1/world/nodes/{id}`. GET ничего не изменяет. Нужны world_read/storage_v2; для принятия — также world_write, но активация кошелька для самого бесплатного принятия не требуется. Общая блокировка записи на время обслуживания сохраняется.

Отложены: миграция и повтор частичного DDL на PostgreSQL/MySQL; публикация флажка/снятие предложения; совпадение типа/площади и исходного поселения; пагинация/поиск; чужое и уже обслуживаемое здание; гонки принятия/снятия/изменения комнаты; повтор после потери ответа; ремонт по принятому снимку после снятия предложения; сохранность покупки, бюджета, предметов и ночлега при принятии. Проверки не запускались.
