# Подготовка переноса счетов и отчётов БД

Дата: 2026-09-27. [Выпуск в test](world-test-release.md): миграции 20–33 применены, install/seed завершены, marker **33**, world_read/world_write включены. Штатный CI и backend deploy успешны. Команды переноса счетов ниже не выполнялись; локальные тесты и игровая приёмка отложены.

## Схема и заполнение счетов

Миграция `m260928_003300_economy_account_backfill` добавляет журнал запусков `economy_account_backfill_run` и журнал обработки объектов `economy_account_backfill_item`. Один активный запуск на мир обеспечивается nullable UNIQUE `active_world_id`; обработка объекта уникальна по `(run_id,node_id)`. Ссылки на мир, объект и операцию используют фактические типы родительских колонок. DDL возобновляемый, на MySQL/MariaDB без внешней транзакции. Миграция сама не переносит данные.

`EconomyAccountBackfill` использует существующий `EconomyHierarchy::provision`. Для активных узлов и их активных предков создаются отсутствующие subject и пары `budget`/`treasury` в Cr с нулевыми суммами и резервами. Первичный финансовый родитель определяется физической иерархией только при отсутствии ранее сохранённого правила. Существующий финансовый родитель может отличаться от физического и сохраняется. Корень мира имеет правило `root`, остальные новые правила — `unconfigured`: ставки и сроки не публикуются автоматически.

До и после операции журналируются subject, счета, указатели правил и текущие версии истории для физической цепочки объекта. Имеющиеся записи сравниваются без изменения сумм, резервов и правил. Старые закрытые версии истории не переписываются. Проверяются цикл, глубина и принадлежность финансовой цепочки одному миру, соответствие текущего указателя версии истории. История без текущего указателя считается ошибкой: исходная связь должна быть восстановлена отдельно, новая связь поверх неё не создаётся. Личные кредиты, долги и проводки не копируются; увеличивается revision узла, если provision создал его финансовые записи.

Одна транзакция обрабатывает один объект, включая недостающих предков, запись операции, журнал и checkpoint. Ошибка откатывает этот объект; предыдущие подтверждённые объекты сохраняются. Повтор команды продолжает с курсора. Порция по умолчанию — 50 объектов, максимум — 200. В начале фиксируется верхняя граница ID; появившиеся позже объекты требуют следующего запуска. Шалаши и узлы с неактивными предками записываются как пропущенные, без создания счетов. Неправильная цепочка останавливает обработку, а не пропускается молча.

## Команды для будущего окна переноса

Запускать из `yii2` в выбранном окружении после backup и остановки world writers/воркеров. Должна быть установлена схема 33. Переносы canonical storage и личного кошелька необходимо завершить либо отменить их штатными командами: параллельный перенос счетов при их заморозке запрещён. На MySQL/MariaDB затрагиваемые таблицы должны использовать InnoDB.

Пример для Linux; `WORLD_ID` и `RUN_ID` заменить фактическими числовыми ID. Это инструкция, не уже выполненный перенос:

```sh
export WORLD_INSTALL=confirmed-world-install
php yii world-setup/flag world_write 0
php yii world-setup/flag economy_tick 0
export WORLD_ECONOMY_BACKFILL=confirmed-zero-accounts
php yii world-audit/accounts WORLD_ID 0 100
php yii world-setup/accounts-begin WORLD_ID
php yii world-setup/accounts-backfill RUN_ID 50
php yii world-setup/accounts-status RUN_ID
```

Повторять `accounts-backfill` с тем же RUN_ID до `status=completed`. Если последняя порция ровно исчерпала лимит, следующий вызов зафиксирует завершение. `accounts-begin` возвращает существующий активный запуск; после завершения создаёт новый. `accounts-status` — только чтение, специальное окружение подтверждения не требуется. Для begin/backfill нужны оба явных контекста и выключенные постоянные `world_write`/`economy_tick`, даже если переменные окружения приложения уже отключают функции. Блокировки каталога и реестра мира сериализуют запись с совместимыми writers.

`processed_count` включает пропущенные объекты; `created_accounts` учитывает и созданные счета предков. `completed` означает окончание прохода до зафиксированного ID, не готовность всей экономики. После прохода отдельно просмотреть `skipped_count` и журнал причин, затем повторить отчёт по счетам. Команды не активируют игровые флаги. После окна убрать `WORLD_ECONOMY_BACKFILL` и `WORLD_INSTALL` из окружения команды.

## Отчёты только для чтения

- `world-audit/accounts WORLD_ID AFTER_NODE LIMIT`: страница до 200 узлов со статусом `ready`, `needs_backfill`, `invalid`, `shelter` или `inactive_ancestry`. Показывает недостающие роли счетов и ошибки финансовой цепочки. Продолжать через `next_after_node`, пока `has_more=true`. `ready` относится только к структуре счетов/родителей: ставки могут оставаться неопубликованными. Снимок согласован в пределах страницы при транзакционных таблицах, это не сертификат всего мира.
- `world-audit/schema`: версии СУБД/схемы, наблюдаемые таблицы доменов и legacy, типы/знаковость колонок, FK, индексы, движки MySQL и список отсутствующих миграций. Типы сравниваются без integer display width; несовпадения требуют разбора, автоматического ALTER нет. `installation_record_complete` сравнивает историю миграций и marker, но не доказывает полноту всех ожидаемых ограничений. Не запускать одновременно с DDL.
- `world-audit/data`: формат JSON версии 2. Для каждой категории `issues` содержит полное `count`, максимум 1000 строк `sample` и `truncated`. Отдельно проверяются сироты с непустыми user/item ссылками, отрицательные количества, положительный остаток без предмета, дубликаты legacy-позиций и canonical `(storage_id,slot)`, отсутствующее хранилище и неправильный номер позиции. `non_user_stock` показывает остатки с пустым `user_id` и контекст владельца хранилища; отсутствие user само по себе не считается ошибкой, допустимость владения NPC/системы требует доменного разбора. Это не полная сверка имущества.
- `world-audit/baseline AFTER_USER LIMIT`: прежний пользовательский baseline теперь читается в одной REPEATABLE READ транзакции на страницу. Несколько страниц при работающих writers не образуют общий снимок. Он не покрывает весь мир или NPC/system stock. Для общей контрольной точки нужно согласованное окно остановки writers.
- Существующие `world-audit/storage` и `world-audit/credits` сохраняют отдельную роль в переносе legacy-хранилищ и точных денег. Storage reconciliation предназначен для пользовательского переноса: его предположения о владельце нельзя использовать как итоговую приёмку будущих NPC/system stock. При появлении этих writers потребуется расширение сверки.

Согласованность снимков требует транзакционных таблиц. `credit_summary` в общем отчёте — диагностический SQL-агрегат прежнего поля; точную финансовую сверку выполняет отдельный отчёт. Ни один отчёт не исправляет данные и не разрешает активацию автоматически.

## Что остаётся

Миграции 20–33 уже применены на test PostgreSQL. Остаются отдельная приёмка на копии MySQL/MariaDB; отчёты схемы/данных и исходный baseline; переносы хранилищ/денег/счетов и сверка; проверка повторов и обрывов, FK/индексов и конкурентных операций на целевых СУБД; backup/restore, совместимый rollback, контролируемая активация хранения и финансов. Удаление legacy-полей — отдельный этап после периода совместимости. Успешная установка на test не закрывает эти эксплуатационные пункты.
