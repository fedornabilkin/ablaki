# Интеграционная проверка API страниц

Дата: 2026-09-05; повтор на актуальном lock — 2026-09-06. Проверялись совместно изменения общих списков, игр и форума. Production-БД и действующие аккаунты не использовались.

## Результат

Все шесть проверочных скриптов повторно прошли на PHP 8.3.33 с временными SQLite-базами после установки production-зависимостей из актуального `composer.lock`:

Lint прошёл для всех 34 изменённых PHP-файлов, `git diff --check` — без ошибок. Новый код использует синтаксис PHP 7.3; локально проверен PHP 8.3.33, запуск на PHP 7.3 предусмотрен в CI и здесь не считается выполненным.

При заключительной синхронизации master включён уже влитый на GitHub PR #23. Обновлённый lock установлен локально через Composer 2.10.3 с `--no-dev`: Yii 2.0.49.4, jQuery 3.7.1, HTMLPurifier 4.17.0. На этих зависимостях все 139 проверок завершились успешно, без warning/notice/deprecated. Полный Yii dispatch подтвердил работоспособность autoload и сериализатора; дополнительно проверены generated aliases миграций `@fedornabilkin/binds`, `@fedornabilkin/redirect` и `@dektrium/user`.

Проверка создания темы подтверждает обязательный `view=0` и сохранение авторства при попытке передать чужой `user_id`. Она входит в повторный общий запуск на новом vendor.

`frontend-api-routing.php` выполняет полный Yii dispatch: реальные правила strictParsing, filters/авторизацию и REST serializer. Проверены общие публичные и закрытые списки, статистика, подсказки, игры, игровые summary, маршруты forum gift/gifts и heartbeat. Возвращаемый envelope создаётся глобальным DI-сериализатором, содержит `items` и `_meta`, а не зависит от ручного вызова helper в тесте.

Публичные комментарии с токеном получают состояние `gifted_by_me` через optional auth. Авторизованный POST подарка передаёт ровно один кредит, повтор даёт `alreadyGiven` без второго списания/истории. Гость получает 401, GET не вызывает передачу, OPTIONS-проверка форумного POST не требует токена. Публичный список передавших раскрывает только идентификатор, логин и дату; расширение автора комментария не раскрывает его email и кредиты. Игровые DTO не раскрывают мины и скрытый результат незавершённой игры. `/recent` у игр требует авторизации, как остальные игровые страницы.

Проверки подарков дополнительно включают нехватку средств, запрет себе, отсутствующее/скрытое сообщение, откат обеих сторон и истории при сбое, восемь одновременных повторов одной команды. Порядок блокировки: сообщение, затем счета по возрастанию user_id; пара сообщение/донор защищена уникальным индексом. Проверка средств выполняется условным SQL-списанием под транзакцией. SQLite-проверка конкуренции не подтверждает поведение FOR UPDATE на других СУБД.

## Исправления по результатам проверки

- Типы FK в новых таблицах берутся из существующих `user.id` и `forum_comment.id`, сохраняя размер и unsigned. Это устраняет несовместимость MySQL при импортированной схеме; миграции не зависят от legacy `remote_db`.
- Сериализатор подключён через реальную конфигурацию API и проверен полноценным dispatch.
- Биржа сериализует безопасные логины участников; переводы — сумму и только доступный создателю код.
- Неподдерживаемое расширение `Theme.comments` удалено; комментарии загружаются отдельным пагинируемым запросом.
- Новая тема получает обязательный счётчик `view=0` на сервере; клиент не управляет авторством.

## Что требуется перед выпуском backend

1. На отдельной копии целевой PostgreSQL/MySQL проверить новые миграции и конкурентные подарки/ежедневные награды. В доступном локальном окружении не обнаружены серверы, CLI PostgreSQL/MySQL или Docker, поэтому target-engine concurrency не подтверждена.
2. Применить `m260905_120000_create_forum_comment_gift_table`, затем `m260905_180000_create_user_presence_table` до переключения API на новый код. При появившихся подарках автоматический откат gift-таблицы запрещён самой миграцией ради сохранения финансовой истории.
3. Выкатить backend до frontend и проверить разрешённые CORS-заголовки/методы для настроенного отдельного API-хоста. Пагинация больше не зависит от экспонирования `X-Pagination-*`, но CORS самого запроса остаётся обязанностью API/VPS.

Существующие блокеры экономики из `plans/2026-09-05-critical-refactoring.md` не закрываются этим изменением: игры, биржа и обычные переводы всё ещё требуют общей транзакционной защиты create/play/confirm/cancel и проверок конкуренции. Новые списки и summary выполняют только чтение; они не исправляют старые цепочки записи. Их успешный тест нельзя считать разрешением выпуска всей экономики backend без оставшихся проверок.
