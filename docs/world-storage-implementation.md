# Хранение и размещение: реализация 2026-09-27

Второй блок работы в `feature/09-worlds`, после дерева/команд/навигации. Код написан; по поручению владельца lint, тесты, сборки, отчёты, backfill, миграции и команды установки **не выполнялись**. Изменения не опубликованы. Это не завершение S1.

## Реализовано

`CanonicalInventory` — writer для формата storage_v2. Выдача, расход, перенос, разделение и объединение стопок идут через него. Новые физические вещи получают новые inventory IDs; пустые исторические строки не переиспользуются. Перенос сундука сохраняет его inventory ID и внутреннее storage; перенос оборудования сохраняет instance IDs и прочность. Количество установленных вещей равно единице. Стопки в рюкзаке сохраняют размер из текущего каталога, в том числе 10 для действующих станций/инструментов.

`StorageAccessPolicy` проверяет именно владельца вещей. Публичный обзор и `world-manage` не дают права читать/перемещать чужое содержимое. Класс хранения и состояние здания проверяются сервером; у recovery разрешён только выход. Содержимое сломанного сундука можно забирать, помещать новые вещи нельзя. Сундук нельзя вложить в сундук. Установка требует свободного активного world_slot, подходящего типа station/chest/equipment и разрешённого item code, если слот ограничен списком. Текущие предметы занимают одно место; размерные варианты будущего контента пока не добавлены.

`EquipmentInstances` создаёт единицу на каждый tool/station и предмет, используемый каталогом как инструмент/станция. Backfill переносит legacy wear на одну детерминированную единицу (первый inventory ID, первый instance ID), остальные сохраняют полную прочность. Повтор не переносит wear второй раз. Отсутствие вещи при ненулевом wear, изменившийся снимок и несогласованное количество останавливают перенос с ошибкой. Погашенные при расходе экземпляры остаются в истории со статусом consumed. Станция с нулевой прочностью остаётся вещью и не работает; ремонт самих станций и инструментов ещё предстоит.

`StationResolver` выбирает доступный исправный экземпляр. До вступления в мир адаптер допускает станцию в активном рюкзаке; после вступления физическая станция должна находиться в placement. Станции каталога без item_id сохраняют прежнее общественное действие. Отдельная модель общественных мастерских с тарифами ещё не реализована. Выбранные единицы защищаются от списания ингредиентами этой же команды.

`EquipmentExposure` хранит класс защиты, момент расчёта, остаток доли износа и версию черновой политики. При просмотре возвращается серверная проекция; перед использованием/сменой места износ фиксируется транзакционно. Перенос, сворачивание в рюкзак и merge сохраняют остаток. Политика v1: пассивно 4/1/0 в сутки для outdoor/covered/indoor; рабочий коэффициент 2/1/1 и добавка 1/0/0 за партию, базовая норма craft=0, repair=1. Это плановые значения, а не утверждённый игровой баланс. Worker WearJob и отдельный журнал интервалов пока отсутствуют.

При вступлении создаётся открытая площадка на четыре места. Backfill добавляет её ранее вступившим владельцам инвентарей. Бесплатные помещения или навесы не создаются. Для готовых комнат движок учитывает состояние постройки и класс слота, но выдача таких мест будет подключена к платному строительству.

## Действующие пути записи

| Вход | Поведение storage_v2 |
|---|---|
| `Crafting::command` | Сохраняет прежний fingerprint и таблицу craft_command. После проверки replay берёт owner/registry locks, использует CanonicalInventory и конкретное оборудование. Старые request keys не переписываются. |
| `CraftStorage::move/merge`, `CraftInventory::transfer` | Адаптеры в единый writer; legacy переносы адресуют только рюкзак и сундуки в рюкзаке. |
| Служебный `InventoryService::moveItem` | Тот же writer и порядок блокировок. Служебные HTTP add-item/craft остаются закрытыми, как в существующем проекте. |
| Старые ActiveRecord/middleware writers | Прямые save/delete CraftInventory и insert через CraftStorage отклоняются при storage_v2. Чтение доступно; обход единого writer не разрешается. |
| Импорт каталога | Нельзя менять тип/назначение принадлежащих игрокам вещей так, чтобы нарушить учёт экземпляров. Переход между учитываемым оборудованием и обычным предметом требует отдельного переноса. |
| Новые world commands | Quote, source storage, destination, position, quantity, instance ID, revisions и operation ID. Перенос записывает inventory_movement; результат и событие сохраняются вместе. |

При включённом формате источником места служит `storage_id`; `container_id/user_id` остаются совместимой проекцией. Формат определяется сохранённым registry, а не временным отсутствием переменной окружения: установленная станция не превращается обратно в рюкзак при выключении UI-флага. Обратное выключение storage_v2 через setup запрещено. Управление доступностью новых действий остаётся у world_read/world_write и окружения.

## API и интерфейс

[Контракт](api/world-storage.openapi.json): список личных хранилищ, страница содержимого с пагинацией, transfer-preview/transfer и chest-repair-preview/chest-repair. Появились revision keys `storage:<id>` и `inventory:<id>`, а также `changed_storage_ids`. Preview переноса фиксирует выбранные unit IDs; повтор команды сохраняет исходное тело. Repair повторно проверяет материалы, прочность, положение и выбранное оборудование.

Новый экран `/world/storage/:id` и панель принадлежащего игроку объекта показывают места, содержимое, overflow, экземпляры, состояние сундука и ссылку на место. Есть сценарий «выбрать вещь → цель и место → расчёт → подтверждение», включая выбор конкретной единицы. Недостающие материалы и оборудование ремонта подсвечиваются красным. Pending-команды разделены по пользователю, поздние ответы сменившейся сессии не применяются.

Существующая мастерская получает дополнительный проверяемый DTO equipment: доступность установленной станции не подменяется фиктивным количеством в рюкзаке. Размеры и оформление текущего CraftSlotGrid не менялись. Новая страница пока использует отдельный список вещей; её объединение с CraftSlotGrid остаётся FE:C3.

## Подготовка данных — код команд, не результаты выполнения

- Четвёртая миграция `m260927_103000_equipment_exposure` добавляет состояние накопленного износа. Последующий блок добавил пятую миграцию rollout/baseline; полная установка теперь фиксирует `schema_version=5`.
- Backfill сравнивает количества до/после, сохраняет сундуки и переносит wear. Перед повторным проходом позиции владельца временно отсоединяются от storage внутри той же транзакции, чтобы не конфликтовать с уже созданным уникальным индексом.
- `php yii world-audit/storage` формирует отчёт количества экземпляров, принадлежности storage, проекции контейнеров, пустых/дублирующихся позиций, сирот и сундуков. Не исправляет данные.
- `php yii world-setup/storage-index` в согласованном окне остановки всех writers требует успешного отчёта и создаёт UNIQUE(storage_id,slot) вне DDL-транзакции MySQL. Требует обычного `WORLD_INSTALL` и `WORLD_BACKFILL_MAINTENANCE=1`; не включает формат.

Окно backfill должно сохранять остановку всех writers. В четвёртом блоке добавлены сохраняемый baseline, возобновление по владельцам и отдельная активация: [процедура перехода](world-storage-rollout.md). Сбрасывать снимки и продолжать старые записи после частичного переноса нельзя. Прямое включение флага остаётся запрещено. Проверки на копиях MySQL/MariaDB и PostgreSQL и фактический запуск отложены.
