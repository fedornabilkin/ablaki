# Переход хранения: сохранённый baseline и активация

Дата: 2026-09-27. Четвёртый блок `feature/09-worlds`. Описан добавленный код. **Миграции, команды переноса, отчёты, lint и тесты не запускались; выкладки нет.** Это не подтверждение готовности к production. Проверки на копиях MySQL/MariaDB и PostgreSQL остаются DB:C7.

Последующее обновление: экономический блок добавил шестую миграцию; актуальный install marker — `schema_version=6`. Хранение и точный кошелёк активируются независимо: процедура этого документа не включает wallet_ready и не меняет credit-колонки.

## Сохраняемые данные

Миграция `m260927_104000_storage_rollout` добавляет `world_storage_rollout` и `world_storage_baseline`. Версия полной схемы теперь 5. DDL использует существующий WorldMigration: MySQL/MariaDB без внешней транзакции вокруг DDL, PostgreSQL с транзакционной установкой. Большой исходный снимок хранится в LONGTEXT на MySQL и text на PostgreSQL. Новая миграция находится в отдельной директории, не подключена к автоматической выкладке.

Один baseline на пользователя включает исходные inventory ID, item ID, количества и принадлежность содержимого сундукам; существующие сундуки и прочность; постоянную вместимость и исходные сроки аренды; legacy wear; навыки и известные рецепты; значение личных Cr; SHA-256 и число записей craft_command, craft_history, craft_event. Токены, пароли и сообщения в снимок не входят. Фиксируется также hash каталога и настроек всего крафта. Денежное значение сравнивается без арифметики float; переход самого кошелька на точное хранение — следующий этап.

В одной транзакции владельца выполняются чтение исходного состояния, перенос и сопоставление износа, сверка разрешённых преобразований, запись baseline и hash полученного состояния. Последний охватывает также storage_id/позиции, экземпляры, assignment износа, текущую экспозицию и места размещения. Записи baseline не заменяются при повторе. Завершённый пользователь повторно не переносится; при изменившемся результате команда останавливается.

Перебираются все пользователи, включая заблокированных и не имеющих строк inventory. Старый общий cursor больше не определяет завершённость: обработанные владельцы выбираются по baseline, записанному вместе с вещами. Сбой до commit оставляет владельца необработанным; сбой после commit не требует повторного переноса. Старая таблица checkpoint сохраняется как история прежней реализации.

Разрешены только существующие нормализации: позиции и storage_id, начальная вместимость 20 при её отсутствии, материализация ранее виртуального сундука по замороженным настройкам, разделение старой стопки сундуков при первой инициализации. Разделение сохраняет исходный ID одной единицы, создаёт ID остальных и обязано сохранить количества/содержимое. Остальные исходные ID и значения сохраняются. Некорректные владельцы, содержимое потерянного сундука, несогласованный wear и необъяснённая разница останавливают перенос.

## Блокировка записей

Фазы: `idle → frozen → backfill → active`. Блокировка находится в БД, переживает перезапуск PHP и продолжает действовать при сбое любой команды. Crafting проверяет её после поиска ранее завершённой команды; replay остаётся доступен. Заблокированы новые команды мира, служебный InventoryService, импорт каталога, настройки крафта, сохранение/удаление через старый CraftInventory ActiveRecord и seed. WorldFlags сообщает `world_write=false`. JobQueue не выдаёт новые задания; уже выданное задание возвращается в ожидание без штрафной попытки, если перенос начался до выполнения handler.

Это защита известных входов нового приложения, **не блокировка всех SQL-клиентов на сервере**. До реального запуска оператор должен перевести весь сайт в обслуживание, остановить HTTP/cron/worker/служебные writers и регистрацию, дождаться завершения старых транзакций и обновить процессы. Это касается также остальных операций кошелька, которые пока не используют craft_meta. Иначе нельзя утверждать, что снимки Cr неизменны или последний проход сверки согласован. Переменная `WORLD_BACKFILL_MAINTENANCE=1` обозначает выполнение этих условий оператором, а не доказывает их автоматически.

Сервис CraftStorage больше не кэширует формат на всё время своей жизни: повторно используемый экземпляр читает сохранённый признак. После активации формат определяется registry.storage_v2 даже при выключенном UI-флаге окружения. Возвращать storage_v2 в 0 запрещено.

## Подготовленный порядок команд — пока не выполнялся

Все изменяющие команды требуют `WORLD_INSTALL=confirmed-world-install` и `WORLD_BACKFILL_MAINTENANCE=1`, кроме самой установки, которая требует installation context. Перед запуском нужны резервная копия и описанное выше обслуживание.

| Шаг | Команда из yii2 | Действие |
|---|---|---|
| Установка | `php yii world-setup/install` | Устанавливает отдельные миграции, seed и schema_version=5; не включает хранение. |
| Заморозка | `php yii world-setup/storage-freeze` | Проверяет транзакционные таблицы на MySQL/MariaDB, сохраняет hash каталога, включает постоянную блокировку. Повтор продолжает существующий процесс. |
| Перенос | `php yii world-setup/backfill 100` | Переносит следующую пачку владельцев; повторять до `more=false`. |
| Сверка | `php yii world-setup/storage-verify 100` | Сверяет следующую пачку с неизменным baseline и hash после переноса; повторять до равенства migrated_users/verified_users. |
| Индекс | `php yii world-setup/storage-index` | После полной обработки и структурной сверки создаёт UNIQUE(storage_id,slot) вне транзакции; повтор проверяет точное определение существующего индекса. |
| Активация | `php yii world-setup/storage-activate` | Повторяет полную сверку всех baseline и структуры под craft_meta/registry, затем одной транзакцией включает канонический формат и снимает блокировку. |
| Состояние | `php yii world-setup/storage-status` | Показывает фазу и счётчики без выгрузки личных данных. |
| Диагностика | `php yii world-audit/storage` | Показывает структурные расхождения, не исправляет их и не активирует формат. |
| Отмена до переноса | `php yii world-setup/storage-cancel` | Разрешена только до первого перенесённого владельца. После начала остаются возобновление либо восстановление полной БД из резервной копии при остановленных writers. |

Наличие ранее перенесённых строк/экземпляров без baseline останавливает начало: новое исходное состояние не подменяет утраченное старое. Частичный перенос новой процедурой возобновляется с сохранёнными снимками. При несовпадении baseline/hash нельзя удалять их или вручную объявлять проверенными.

Прямой `world-setup/flag storage_v2 1` остаётся запрещён: использовать можно только проверяемый путь активации. `economy_tick` пока не активируется. Новый формат не означает автоматическое открытие UI: приложению всё ещё нужны WORLD_READ/WORLD_WRITE/STORAGE_V2 и соответствующие registry flags.

Последний проход активации намеренно полный и может быть длительным на больших данных; выполнять его следует в окне обслуживания, а время измерить на копии. Успешная промежуточная сверка не заменяет последнюю. Необходимо отдельно проверить гонки, повтор после сбоя DDL и каждой границы транзакции, старые request keys и отсутствие потерь в двух целевых СУБД.
