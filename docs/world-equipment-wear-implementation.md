# Фоновый износ и история прочности

Семнадцатый блок, 2026-09-27: BE:K9, DB:I7, FE:H9. Продолжение K5 без изменения действующих норм. Код подготовлен в `feature/09-worlds`; schema marker 18. Test остаётся на marker 17. Тесты, lint, сборка, миграции, коммиты и выкладка нового блока не запускались по текущему порядку работы с владельцем.

## Единый расчёт

EquipmentExposure остаётся единственным расчётом временного износа: 4 единицы за реальные сутки на улице, 1 под навесом, 0 внутри/в переносном инвентаре. Это 86400 секунд, независимо от длины игровых суток ночного календаря. Сначала погашается прошедший интервал старой среды, затем записывается новая. Дробный остаток 0…86399 сохраняется при переносе и ремонте. В помещении сохраняется прежний износ за работу; станция при ремонте сундука проходит тот же use.

Новый worker не начинает второй расчёт и не добавляет урон до существующего settled_at. Он вызывает settle до текущего серверного времени, как ручные действия. Если наступил предел прочности, экземпляр остаётся active с durability=0: вещи не удаляются и не переносятся. Существующие resolver/preview запрещают работу сломанной станции. Шалаш теряет защиту по уже сохранённому protected_until, worker не переписывает прошлые ночи.

## Планирование и блокировки

При запуске `WORLD_WORKER=1 php yii world-worker/run` и одновременно разрешённых world_write/storage_v2 выполняется один обход не более 100 активных экземпляров с положительной прочностью и daily_wear. Persistent `world_wear_scan.after_instance_id` продолжает обход между CLI-запусками и возвращается к началу после конца списка. Обход под craft_meta → registry только ставит задания, не меняет предметы другого владельца.

Срок job: `settled_at + ceil((86400-remainder)/daily_wear)`. Идентичность `instance:{id}:at:{timestamp}`, payload содержит только instance_id, owner записан в job. JobQueue применяет прежний lease/fencing и порядок craft_meta → owner → registry → job. После расчёта checkpoint, история, outbox и следующее задание фиксируются вместе с отметкой done. Повтор доставки не списывает износ второй раз. Полный простой закрывается одним расчётом до now, без тысяч промежуточных задач.

При переносе внутрь, расходовании или смене владельца устаревшее задание не меняет чужие вещи. Действующие пути переносов сохраняют владельца; будущая передача другим игрокам потребует отдельной интеграции планирования/истории. Сканер на следующих проходах обнаруживает вновь вынесенное наружу или отремонтированное оборудование. Задания могут рассчитываться позже срока при большом количестве экземпляров, но GET всё равно показывает проекцию текущей прочности. Флаги/maintenance приостанавливают запись; время не останавливается. `economy_tick` не требуется, деньги не затрагиваются. Cron/сервис на сервере этим блоком не устанавливается; используется существующий CLI worker.

## Журнал

`craft_equipment_wear_history` хранит завершённые интервалы elapsed и события location/work/repair: owner, instance, серверные границы, прочность и остаток до/после, среды и ставки, policy version. Запись находится в транзакции соответствующего изменения предмета, а не в GET или отдельной отложенной записи. Даже дробный elapsed сохраняется, если действие погасило часть единицы износа. Перемещение между одинаковыми классами среды не создаёт фиктивную смену среды.

Старые перемещения не восстанавливаются: первый elapsed может суммировать время от ранее существовавшего checkpoint, параметры которого уже сохранены в craft_equipment_exposure. Миграция не сбрасывает прочность, остаток, settled_at или policy. До наличия новой таблицы старые canonical writers продолжают работу без журнала; после установки новые изменения пишутся атомарно. События не означают новых покупок или восстановления старой истории.

Схема 18 additive: новая таблица журнала и singleton cursor; FK с реальными типами и возобновляемые индексы. MySQL/MariaDB DDL выполняется без внешней safeUp-транзакции; существующие таблицы и миграционная история не меняются. Marker повышается только успешным world-setup/install.

## API и интерфейс

[OpenAPI](api/world-equipment-wear.openapi.json): `GET /world/equipment/{id}/wear`, только текущий владелец активного экземпляра с доступом к storage. Для установленного шалаша используется отдельная проверка deployment/владения стоянкой; скрытый shelter storage не открывается общему API размещения. Чужой администратор не получает историю частного имущества.

Возвращаются проекция прочности, текущая ставка/среда, адрес хранилища или стоянки и история по 20 записей. Поиск по названию причины, kind-фильтр, порядок id DESC; count и записи ограничены верхним ID запроса. Для текущей проекции unit/exposure читаются одним SQL, чтобы фоновые записи не смешали старую прочность с новым checkpoint.

Frontend `/world/equipment/:id/wear` открывается настоящими ссылками из списка экземпляров в storage и панели шалаша. Есть причина, интервал, прочность до/после, смена среды/ставки, серверное время, состояния загрузки/ошибки/пустого журнала. Поиск/фильтр/страница хранятся в URL через useListQuery, ListFilters и PagePager. Runtime parser валидирует ответ, смена аккаунта/маршрута отсекает запоздалые запросы.

## Границы и отложенная приёмка

Не добавлялись самостоятельный временной износ сундуков, новые тарифы, произвольное редактирование защиты, повреждение капитальных зданий или пауза NPC-производства. Сундуки сохраняют свои действующие нормы; при их ремонте журналируется использование конкретных инструментов/станций. Общие правила совместимости K4, подключение активации K6 и полная приёмка K5 остаются открытыми.

Далее проверить на обеих СУБД: повтор jobs и конкурентный перенос/крафт; дробные интервалы outdoor→covered→indoor; нулевую прочность и ремонт шалаша; длительный простой; флаги/maintenance; обход более 100 экземпляров; rollback после записи журнала; права доступа и пагинацию; отсутствие повторного износа в расчёте ночей. Эти проверки ещё не выполнялись.
