# Соглашение по релизу backend

## Быстрая тестовая выкладка — решение владельца от 2026-10-26

Перед test обязательны проверка изменённого PHP, deploy guards, установка по lock/platform и короткие сценарии авторизации, наград, возвратов и маршрутов API. MySQL/PostgreSQL, полный игровой маршрут, конкурентные проверки и Composer audit запускаются после успешного deploy через `backend-full.yml`. Перед production полный прогон остаётся обязательным.

Готовность test определяется успешным job `Deploy backend to test`, сообщением READY и HTTP smoke, а не окончанием всего workflow: дополнительные тесты могут ещё выполняться. Сообщать о доступности версии сразу после deploy; полный отчёт оформлять отдельно. Если дополнительные проверки обнаружат ошибку, исправлять её следующим коротким выпуском.

Установленный мир повторно используется только при совпадении fingerprint установочных файлов и успешной read-only проверке схемы, миграций, флагов, storage/wallet и профиля. Pending или изменения запускают прежнюю полную подготовку. Бэкап/restore и сброс данных не добавляются. Изменённый файл профиля публикуется существующим администратором без выпуска кредитов; неизменённый файл сохраняет правки профиля из админки. Worker завершает текущую партию перед остановкой. Последующие пункты с прежними проверками применяются с учётом этого решения.

## Ускорение test — уточнение владельца 2026-10-21

По поручению владельца «Проработай варианты оптимизации выкладки бэка, убери этап бэкапа БД, например» автоматический test deploy больше не создаёт dump и не восстанавливает его во временную БД для двойного прохода проверки. Это заменяет прежнее требование резервной копии в тестовом маршруте. Уже существующие копии не удаляются. Блокировка активации, отметка незавершённой установки, baseline/checkpoint переноса и проверки реального состояния данных сохраняются.

В CI независимая группа API/SQLite выполняется параллельно с PostgreSQL и MySQL; состав проверок сохранён, ошибка любой группы блокирует deploy. SSH-соединение повторно используется только в пределах job на временном runner. Серверная SSH-конфигурация, Dockerfile, entrypoint, инфраструктура и production-БД в этом пакете не меняются. [План, замеры и следующие варианты](../docs/plan/2026-10-19-test-deployment-optimization.md).

## Автоматическая подготовка test — уточнение владельца 2026-09-27

По прямому поручению владельца test deploy включает перенос/активацию существующего инвентаря и кредитов, нулевые счета мира, начальный тестовый контент и постоянный worker. Для этого разрешены остановка test nginx/PHP/worker, включение игровых настроек test и запуск отдельного worker-контейнера. Ранее разрешённый резервный dump исключён из автоматического test deploy уточнением 2026-10-21 выше. [Порядок](../docs/operations/world-test-autostart.md). Это исключение относится только к тестовому окружению; прежние ограничения production сохраняются.

## Текущее решение владельца

- По прямому требованию от 2026-09-06 Docker и запуск приложения восстановлены из c875c7c — состояния до первой автоматизации 4640955.
- Обычный автодеплой выполняет только git pull и make up в существующем checkout.
- Не менять Makefile, Dockerfile, Compose, entrypoint, зависимости, схему миграций и инфраструктуру ради автоматизации этих команд. Улучшения выполняются только по новой просьбе владельца.
- По поручению от 2026-10-24 обновление PHP 8.3.36 — отдельное разрешённое изменение runtime: сборка PHP/Composer, совместимый lock и смена vendor через `deploy/php-runtime-upgrade.sh`. При совпадении версии и fingerprint этот этап ничего не пересобирает. Перед заменой зависимостей останавливаются PHP, nginx, Composer и тестовый worker; при ошибке восстанавливаются прежние образ и vendor. БД не копируется, не восстанавливается и не перезапускается.
- Разработка продолжается в master. Сохранять локальные изменения; перед push проверять затронутые файлы.

## Существующий запуск

- Production checkout: /var/www/api.ablakin.ru. Владелец подтвердил, что и прежний рабочий ручной запуск выполнялся из этой папки.
- Test checkout: /var/code/ablaki. Production frontend: /var/www/ablakin.ru; test frontend: /var/code/ablaki-front (только готовая статика, по уточнению владельца от 2026-09-06).
- make up снова вызывает docker-compose up --detach --remove-orphans и docker-compose ps.
- Инициализация Yii и пять команд миграций остаются в исходном docker/php/entrypoint.sh. Отдельных preflight/start/migrate-скриптов нет.
- Исходный PHP Dockerfile, Composer-контейнер, порты, volumes и фиксированная подсеть восстановлены без модернизации.
- Существующий db-компонент Yii выбирает MySQL при заполненных MYSQL_DB_HOST/MYSQL_DB_NAME, иначе PostgreSQL по PG_DB_*. Локальные main-local.php могут переопределять подключение.
- Не менять .env, локальные настройки, историю миграций, данные или имена Docker-проекта в ходе обычного деплоя.
- В исходной production .env COMPOSE_PROJECT_NAME отсутствовал — это подтверждено владельцем. Не добавлять его ради имени apiablakinru; при откате удалить добавленную во время автоматизации строку, восстановив её отсутствие.
- Если настройка на VPS была изменена во время неудачной автоматизации, отдельно восстановить её прежнее значение по реальным контейнерам/конфигурации. Не угадывать его и не удалять сети или volumes.

## Автоматизация и проверки

- Push master запускает production. Ручной test использует ветку, уже выбранную в test checkout. Для окружений сохраняются отдельные BACKEND_* и TEST_BACKEND_* SSH secrets.
- Deploy-скрипт хранится в /opt/ablaki-backend или /opt/ablaki-backend-test. Он выполняет git pull --ff-only origin <branch>, затем make up. При ошибке pull запуск не продолжается.
- Дополнительные проверки, установка vendor, создание backup, сборка образов, остановка контейнеров, принудительное пересоздание и изменение .env из deploy-скрипта исключены.
- Проверки CI выполняются на GitHub, без подключения к БД VPS. PHP lint и поведенческие проверки обязательны для изменённого прикладного кода.
- Добавленные для автоматизации backend /health и SHA-маркер удалены. Frontend deploy не зависит от них.
- Успешный make up не доказывает успешность миграций: исходный entrypoint не прерывает запуск PHP-FPM при их ошибке. Это исходное поведение сохранено по просьбе владельца, без маскировки ошибок или изменения migration history.
- Прежние изменения .env, уже созданные Docker-ресурсы, применённые миграции и установленные зависимости не отменяются Git-откатом. Их состояние проверяется отдельно.
- [Актуальная инструкция](../docs/operations/production-test-deployment.md).

- Ветка test предназначена только для тестовой выкладки. В дальнейшем запрещено вливать test в master; production выпускается только из master. Разовое слияние текущей тестовой ветки в master допускается только по отдельному решению владельца.

## Порядок работы с ветками

Используем GitLab Flow. Рабочую ветку создаём от актуального master с понятным префиксом и номером месяца. Изменения выполняем в рабочей ветке, затем делаем коммит и push. После этого рабочую ветку вливаем в test и проверяем результат в тестовом окружении. После успешной проверки ту же рабочую ветку вливаем в master. Сразу после merge в master рабочую ветку удаляем локально и в origin. Ветку test в master не вливаем; исключения требуют отдельного решения владельца.
## Архитектурные правила разработки

- Для новых изменений применяем подходящие паттерны проектирования и сохраняем существующие границы модулей.
- Соблюдаем принципы SOLID и GRASP: одна ответственность, явные зависимости, слабая связанность, высокая связность и корректное распределение обязанностей.
- Стремимся к слоистой архитектуре: контроллеры отвечают за HTTP-контракт, сервисы — за сценарии и транзакции, модели и репозитории — за данные, инфраструктурный код — за внешние ресурсы.
- Архитектурное решение должно соответствовать задаче и не добавлять лишние абстракции без практической пользы.
- При изменении существующего кода сначала сохраняем его публичный контракт, а нарушение совместимости оформляем отдельным согласованным изменением.
