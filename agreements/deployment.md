# Соглашение по релизу backend

## Подготовка

- По решению владельца разработка ведётся непосредственно в master, предварительно синхронизированном с origin/master. Рабочие и релизные ветки создаются только по отдельной просьбе.
- Сохранять пользовательские изменения рабочей копии и локальные настройки. Не заменять их принудительным сбросом ради публикации.
- Перед выпуском проверять API, зависимости и ожидающие миграции. Обновление PHP и инфраструктуры планировать отдельно от обычного деплоя.

## Проверки и совместимость

- PHP lint и тесты затронутых операций обязательны.
- Конкурентные операции проверять на целевом PostgreSQL/MySQL; SQLite-тест не заменяет проверку движка production. Тесты не запускаются на production-БД.
- До выпуска проверить затронутые auth, ставки, завершение и отмену игры, биржу, ежедневный бонус.
- При изменении API сохранять совместимость действующего клиента либо выпускать backend до нового frontend.
- Отдельно проверять Yii debug/env и секреты; frontend workflow их не изменяет.

## Окружения

- Production backend — `/var/www/api.ablakin.ru`, существующая MySQL по `MYSQL_DB_*` production `.env`, `APP_ENVIRONMENT=production`.
- Test backend — `/var/code/ablaki`, существующая PostgreSQL по `PG_DB_*` test `.env`, `APP_ENVIRONMENT=test`.
- Сохранять действующие `.env`, локальные конфиги Yii, загрузки, имена сервисов, Compose project, volumes, сети и порты. `COMPOSE_PROJECT_NAME` не является обязательной новой настройкой; не назначать новое значение вместо существующего имени.
- Test использует собственные secrets/variables с префиксом `TEST_BACKEND_`; production fallback запрещён. Адреса теста: API `http://94.250.251.94:3180/`, admin `http://94.250.251.94:3195`, frontend `http://94.250.251.94:3181`.
- Production vendor устанавливается с `--no-dev`, test — с dev-зависимостями текущего lock для существующего Yii debug. Локальные настройки debug и разрешённых IP сохраняются.
- Служебные каталоги — `/opt/ablaki-backend` и `/opt/ablaki-backend-test`: incoming, releases и состояние публикации. Они отделены от checkout.
- Production frontend остаётся в `/var/www/ablakin.ru`, test frontend публикуется только в `/var/code/ablaki-front/project/dist`.

## Публикация

- Push master запускает backend CI и production SSH-деплой. Вручную production запускается только из master, test — из выбранной существующей ветки. [Инструкция](../docs/production-test-deployment.md).
- По уточнению владельца от 2026-09-06 текущий процесс сохраняет обычный запуск `make up` **с миграциями** после обновления кода и vendor. Backup/dump перед деплоем не выполняется.
- Создание БД, копирование данных между окружениями, SQL fingerprint и изменение подключения не входят в публикацию. Не запускать `make init` или `down --volumes` для обновления существующего приложения.
- Код и vendor должны соответствовать проверенному commit SHA; перед установкой проверяется checksum артефакта. На время замены кода/зависимостей приложение останавливается.
- Ошибка миграции останавливает запуск. После исправления повтор применяется к тому же окружению; миграции не отключаются и не помечаются выполненными для обхода ошибки.
- Успех подтверждается внутренним и внешним API, SHA и `environment`. Полный `/health` и контракты списков остаются обязательной проверкой готовности перед публикацией нового frontend.
- Предыдущие SHA и vendor не являются копией БД. Автоматического отката данных нет; операции восстановления согласуются отдельно. Существующие архивы/копии этот процесс не удаляет.
- Доступы GitHub/VPS и первый серверный запуск проверяются отдельно; наличие workflow не подтверждает работающий автодеплой.
- Результаты проверок и оставшиеся блокеры фиксируются в планах; успешный lint сам по себе не подтверждает готовность production.
